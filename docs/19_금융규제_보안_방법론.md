# 19. 금융규제·보안 방법론 (실서비스 기준, 초안 2026-11-08)

`18_금융규제_보안_고려사항.md`가 "무엇을 고려해야 하나"라면, 이 문서는 **"어떻게 대응하나"**다.

- 기준은 실제 서비스다(PoC/실서비스 구분 없음).
- 법률 자문이 필요한 항목(18번 4절 L1~L15)은 **잠정 방침**을 정해 두고, 자문 결과에 따라 바꾼다. 잠정 방침은 항상 보수적인 쪽(정보 제공 표현 유지, 비공개 기본값)으로 잡는다.
- 근거 표시는 18번과 같다: ✅ 원문 확인 / ⚠️ 일반 지식(원문 확인 전) / 🔲 미확인.
- ⚠️ 이 문서의 구체 수치(보관 기간, 호출 한도 등)는 **설계 제안**이지 법정 기준이 아니다. 법정 기준은 6절 자료를 받아 확인한 뒤 맞춘다.

## 0. 대응 원칙 (모든 항목에 공통)

| # | 원칙 | 뜻 |
|---|---|---|
| P1 | 결정을 대신하지 않는다 | AI는 정리·계산·비교까지. 결정은 가족의 동의로만(`CLAUDE.md` 4절 6번). 금융위 AI 가이드라인의 "보조수단성(최종 결정은 사람)" ✅과 같은 방향 |
| P2 | 권유가 아니라 정보 제공 | 가입 연결·수수료·"추천" 표현을 쓰지 않는다. 상품은 조건 비교까지, 가입은 본인이 직접 |
| P3 | 최소 수집·최소 전달 | 필요한 정보만 받고, LLM에는 역할마다 필요한 것만 보낸다(`03` A-2 경계) |
| P4 | 본인이 통제한다 | 공개 범위·동의·철회·삭제를 구성원 각자가 직접 |
| P5 | 검증 가능한 AI | 숫자는 엔진, 근거는 인용 글자 일치, 위반 시 화면에 안 나간다(`07`) |
| P6 | 증거를 남긴다 | 누가 언제 무엇에 동의했는지, 어떤 버전의 합의안인지, AI가 무엇을 근거로 썼는지를 사후에 보일 수 있게 |
| P7 | 자문 결과로 되돌릴 수 있게 만든다 | 법적 판단이 불확실한 기능은 **끄는 스위치**를 먼저 만든다(2-2절) |

## 1. 금융규제 대응

### 1-1. 서비스 기능 경계표 (가장 먼저 만들 것)
서비스가 하는 일을 기능 단위로 나열하고 **허용 / 조건부 / 금지**를 정한 표를 한 장 만든다. 모든 화면 문구·AI 출력 검사가 이 표를 기준으로 한다.

| 기능 | 잠정 판정 | 조건 |
|---|---|---|
| 가족 의견 정리, 쟁점 분석 | 허용 | |
| 미래 계산(현금흐름·달성 시점) | 허용 | 가정값·기준월 공개, "예측이 아닌 가정에 따른 계산" 문구 |
| 목표 숫자 기준 제시(공공 통계) | 허용 | 출처 원문 확인되는 것만(`CLAUDE.md` 4절 15번) |
| 방법 설계(레버·조건) | 조건부 | 범주·원리 수준까지. 특정 상품·종목 지정 금지 |
| 투자 비중 약속(예: 여윳돈 주식 20%) | 조건부 | 가족이 정한 값을 표기하는 것으로만. AI가 비중을 "권하는" 문장 금지, 변경 시 근거를 가족 입력에서 가져온다 |
| 실제 상품 조건 비교 | 조건부 | 2-2절 기준. 자문 전까지는 **끌 수 있는 구조** |
| 상품 가입 연결·신청 대행 | 금지 | 판매대리·중개 쟁점 ✅(금소법 제2조: 계약 체결의 대리·중개) |
| 제휴 수수료·광고 수익 | 금지(현재) | 도입하려면 L14 자문 후 |
| 제도 안내(정책금융 등) | 조건부 | 원문 인용 + 기준일 + "신청은 기관에서" |

### 1-2. 문구 통제
- **금지 표현 목록**(추천, 가입하세요, 유리합니다, 손해 없음, 수익 보장 등)과 **필수 표현**(가입 판단은 본인, 정보 기준일, 출처)을 만든다. 기능 경계표와 함께 관리.
- 이미 있는 서버 검사 G12(금융회사·브랜드 이름)와 같은 방식으로 **금지 표현 검사**를 모든 AI 출력에 붙이고, 위반하면 화면에 나가지 않게 한다. 돌연변이 테스트(일부러 금지어를 섞어 걸러지는지)로 확인.
- 정적 화면 문구(소개 페이지, 가격, 효과 설명)는 같은 목록으로 검사하는 스크립트를 둔다.

### 1-3. 상품 비교 화면 기준 (L1 잠정 방침)
- 금소법 제22조①: 금융상품판매업자등이 아닌 자는 금융상품 광고를 하지 못한다 ✅. 이 화면이 광고인지는 **우리가 정하지 않고 자문으로 받는다**. 그때까지 기준:
  - 정렬 기준을 화면에 공개한다(목표 적합도 계산 방식), 금리 1등 순위처럼 보이게 하지 않는다.
  - 상품 정보는 **공시 원본 출처와 기준일**을 함께, 우대 조건·자격은 원문 그대로.
  - 이해관계 없음(수수료 없음)을 명시하되, "광고가 아니다"라고 단정하지는 않는다.
  - **끄는 스위치:** 자문 결과가 불리하면 상품 이름을 숨기고 **범주 통계와 조건 체크리스트만** 보여 주는 모드로 즉시 전환할 수 있게 설정으로 분리한다(공개 사이트에서도 동일).
- 설계 결정이 필요한 부분은 임의결정으로 기록한다(`임의결정_기록.md`).

### 1-4. AI 가이드라인 이행 (금융위 7대 원칙 ✅ 대응표)
가이드라인은 자율규제지만 B2B 제휴 때 입증 자료가 된다. 원칙마다 **우리 통제 장치 → 증빙**을 연결한 표를 유지한다.

| 원칙 | 우리 통제 장치(현재/설계) | 증빙 |
|---|---|---|
| 거버넌스 | 책임자 지정, AI 변경 승인 절차(모델·프롬프트 변경 시 재검증) | 변경 기록, 담당자 명부 |
| 합법성 | 이 문서 + 법률 자문 | 자문 의견서, 기능 경계표 |
| 보조수단성 | 결정은 가족 동의로만, AI가 숫자·상품을 정하지 않음 | 화면 흐름, 합의 기록 |
| 신뢰성 | 숫자는 엔진, 인용 검사, 골든 테스트, 근거 원문 | 테스트 결과(`pytest`, `kb_eval`) |
| 금융안정성 | 해당 낮음(대출 심사·거래 없음). 외부 AI 장애 시 대체 동작 | 장애 시나리오 문서 |
| 신의성실 | 가족 이익 중심 설계, 수수료 없음, 불리한 결과도 표시 | 문구 검사, 설계 문서 |
| 보안성 | 3절 | 시험 결과 |

- 외부 AI(Anthropic) 사용은 가이드라인이 "법령 준수 여부를 직접 확인하고 계약에 반영"하라고 한다 ✅. 제3자 계약 점검표(가이드라인 예시 항목)로 **공급자 계약 점검**을 한다: 서비스 제공 국가, 보안·프라이버시, 사업 중단 시 데이터 반환, 사고 시 정보 공유·책임, AI 법규 준수.
- 상용 AI API 의존은 감독당국 보고 정보로 꼽힌다 ✅. 제휴사가 요구할 때 낼 **AI 활용 구조 문서**(어느 역할에 어떤 모델, 어떤 데이터가 가는지)를 `06_LLM역할.md`에서 뽑아 만든다.

### 1-5. AI 기본법 대응 (L8 잠정 방침)
- 고영향 AI 해당 여부를 문서로 판단한다(가이드라인의 판단 절차: 영역 해당 → 의사결정 의존도 → 민감정보 사용 여부 ✅). 잠정 결론: **대출심사·신용평가 기능 없음, 결정은 가족** → 고영향 아님. 근거를 서면으로 남기고, 변경(예: 대출 가능 여부 판정 기능 추가) 때 재판단.
- 생성형 AI 고지·결과물 표시 ✅: ① 서비스 시작 때 "AI가 작성합니다" 사전 고지(동의 화면과 통합) ② AI가 쓴 글에는 화면에서 AI 작성 표시. 구체 형식은 시행령 확인 후(자료 5번).

### 1-6. 마이데이터 (L3·L4 잠정 방침)
- 초기 경로는 **허가 사업자 제휴**(`03` B-1). 제휴 전까지 금융정보는 **직접 입력**만.
- 전송요구는 **본인만** 할 수 있다고 가정하고 설계: 가족이 대신 연결하지 않는다.
- 가족방에 올릴 때는 구성원별 **공개/비공개 선택**(현재 구현)에 더해 "다른 가족에게 보이는 것에 동의" 문구를 별도 동의로 받는다.
- 부모 정보 지속 열람: 자문 전까지 **자녀는 부모의 원본 금액을 보지 않고** 부모가 공개를 고른 항목만 본다(현재 구조 유지). 열람 기록을 부모가 볼 수 있게 한다.

### 1-7. 데이터 기준일·갱신
- 모든 공시·제도 데이터에 **기준일과 갱신 주기**를 붙이고, 기준일이 기한(예: 상품 30일, 제도 90일 ⚠️ 제안)을 넘으면 화면에서 "오래된 정보" 표시 또는 숨김.
- 법령 RAG: 법령 개정 확인 절차(분기 1회 ⚠️), 조각에 시행일 표시.

### 1-8. 당국 협의 준비
- 비조치의견서·혁신금융서비스 신청 때 낼 **설명 패키지**: 기능 경계표, 화면 흐름, 데이터 흐름도, AI 활용 구조, 검증 구조. 이 문서들을 한곳에 모아 버전 관리한다.
- L1·L2 자문 결과에 따라 신청 여부를 정한다(L13).

## 2. 개인정보 대응

### 2-1. 동의 설계
- **구성원별 개별 동의**를 받는다(가족 대표가 대신 동의 불가). 항목 분리: ① 서비스 이용(필수) ② 대화·요약 AI 처리(필수) ③ 국외 이전 고지·동의(L5 결과에 따라) ④ 가족에게 공유되는 요약(필수, 내용 확인 후) ⑤ 금융정보 공개 범위(선택) ⑥ 건강 관련 정보(선택).
- 동의 기록: 누가, 언제, 어떤 문구 버전에 동의했는지 저장(P6). 문구가 바뀌면 재동의.
- **방장이 다른 가족을 대신 적는 정보:** 초대받은 사람이 수락 화면에서 "방장이 입력한 내용"을 확인하고 정정·삭제할 수 있게 한다. 수락 전에는 AI 처리·공유 없이 보관만(보관 기한 짧게).

### 2-2. 만 14세 미만 (L7 잠정 방침)
- 법정대리인 동의 의무가 있다는 것은 개인정보위 점검 보도에서 확인했으나 법령 원문은 🔲.
- 잠정 방침: **계정을 가진 구성원은 만 14세 이상만.** 14세 미만 자녀는 계정 없이 "가족 구성"의 숫자(나이)로만 입력하고, 이름은 별칭 허용, 자유 텍스트 없음. 연령 확인 절차(생년 입력 + 확인 문구)를 둔다.

### 2-3. 민감정보
- 병원비·간병은 **금액·기간 항목**으로 받고, 질병명·진단명 입력은 막는다(안내 문구 + 입력 검사).
- 대화(자유 텍스트)에서 건강·종교·정치 등이 나오면 **요약 생성에서 제외하는 규칙**을 역할 1 프롬프트에 두고 출력 검사(키워드·분류)로 확인. 구성원이 직접 "공유해도 좋다"고 한 것만 가족 요약에 남긴다.

### 2-4. LLM으로 보내는 데이터 (L5 잠정 방침)
- 이미 하는 것: 역할별 입력 조립, 원문은 해당 역할에만, 이름 가명화.
- 추가: ① **자유 텍스트 PII 차단**(주민번호·전화·계좌·카드 패턴 탐지 → 전송 전 마스킹 또는 입력 차단; 가이드라인도 입력 경고를 예시로 듦 ✅) ② 재식별 위험 점검(나이·직업·자산 조합) ③ 공급자 설정: 학습 미사용·보관 최소(가능한 최단), 계약서(DPA) 확보 ④ 국외이전 고지를 처리방침과 동의 화면에 넣는 초안을 미리 준비해 두고 자문 후 확정.
- 공급자 교체를 대비해 어떤 데이터가 어떤 공급자로 가는지 **데이터 흐름도**를 유지.

### 2-5. 보관·파기 (초안, 법정 기간은 자료 확인 후)

| 데이터 | 보관 | 파기 |
|---|---|---|
| 대화 원문 | 본인 키 암호화, 서비스 이용 중 | 가족방 해산·탈퇴 시 즉시, 또는 본인 삭제 |
| 요약(가족 공유본) | 가족방 존속 중 | 해산 시 본인 요약 삭제, 합의안은 선택 |
| 금융 원본 | 구성원별 | 탈퇴·해산 시 즉시 |
| 합의안·서명 | 버전별, 해시 | 해산 시 선택 보관 |
| 호출 로그·사용량 | 개인정보 없이(식별자 해시) | 정해진 기간(예: 90일 ⚠️) 후 |
| 동의 기록 | 법정 보관 의무 확인 후 | 의무 기간 후 |

- 탈퇴·거부 시 처리: 본인 데이터 삭제, 이미 공유된 요약은 가족방에서 "탈퇴한 구성원"으로 표시하고 내용 삭제(합의안 서명 이력은 유지 여부를 자문).

### 2-6. 정보주체 권리·운영
- 열람·정정·삭제·처리정지를 **서비스 화면에서 본인이 직접** 하도록 만든다(가족이 대신 불가). 응답 기한과 본인 확인 절차를 문서화.
- 처리방침(AI 사용·국외이전 포함) 초안 작성, 개인정보 보호책임자 지정, 수탁사(Anthropic, 호스팅) 목록 관리. 영향평가·ISMS-P 필요 여부는 규모 기준을 자료(2번, 11번)로 확인 후 판단.

## 3. 보안 대응

### 3-1. 방법: 위협 모델 → 통제 → 시험 → 운영
1. **자산 분류:** 4등급 ⚠️ 제안 — ① 대화 원문·금융 원본(최상) ② 가족 공유 요약·합의안 ③ 계산 결과·설정 ④ 공개 자료(상품 공시, 법령). 등급마다 저장·전송·접근·로그 규칙이 다르다.
2. **행위자·경로:** 외부 공격자, 악의적 가족 구성원, 초대받은 제3자, 공급자 장애·유출, 내부 운영자, 프롬프트 속 공격자(간접 인젝션).
3. **통제:** 아래 3-2~3-6.
4. **시험:** 3-7.
5. **운영:** 3-8.

### 3-2. 인증·권한
- 역할 기반: 본인 / 가족 구성원 / 방장 / 운영자(서버 전용). 방장 권한은 초대·방 설정에 한정하고 **다른 구성원 데이터 열람 권한은 없다.**
- 초대 링크: 서명·만료·1회 사용, 재발급 시 기존 무효.
- 본인 인증(실서비스): 가입 때 본인 확인, 중요 작업(공개 범위 변경, 서명, 삭제)은 재인증.
- **강요 방지:** 자녀가 부모에게 정보 연결을 압박하는 것을 막기 위해 연결·공개는 항상 본인 화면에서 본인이 선택하고, 선택 기록을 본인에게 알림.
- 운영자 접근: 원문 대화는 운영자가 복호화할 수 없는 구조(`03` B-2), 예외 접근은 승인·기록.

### 3-3. 데이터 보호
- 전송 TLS, 저장 암호화, 키는 용도별로 분리(대화 원문 / 금융 원본 / 서명), 백업도 암호화·파기 대상.
- 합의안·서명: 버전 해시에 서명 묶기.
- 로그·사용량 장부: 개인정보 마스킹, 식별자는 해시. 오류 추적 도구에 본문 전송 금지.
- 클라이언트: 민감정보를 브라우저에 남기는 범위 최소화, 공용 기기 대비 자동 만료와 로그아웃 시 삭제.

### 3-4. AI 보안 (가이드라인 예시 ✅를 기준으로)
- **프롬프트 인젝션:** 현재 방어(가족 글 속 지시 무시 규칙 + 출력 스키마 검사 + 부작용 없는 도구)에 더해 ① 의심 패턴 1차 필터 ② 간접 인젝션(RAG 조각, 다른 구성원 요약) 시험 세트 ③ 도구는 계산만 가능하도록 유지.
- **정보 유출 방지:** 공유 단계 프롬프트에 원문·비공개 항목이 안 들어가는 자동 테스트(있음)를 모든 역할로 확대, 출력에서 시스템 프롬프트·내부 ID 노출 검사.
- **출력 안전:** 화면 이스케이프, 링크·이미지·스크립트 삽입 금지, 금지 표현 검사(1-2).
- **남용 방지:** 계정·IP별 호출 제한, 입력 길이 제한, 비용 상한(구현 있음), 비정상 호출 탐지·경고·차단 단계(가이드라인이 예로 든 5회/10회 경고·차단 구조 ✅를 참고해 우리 수치를 정한다 ⚠️).
- **모델 변경 관리:** 모델·프롬프트 변경 시 골든 테스트와 평가 세트 재실행 후에만 배포.

### 3-5. 공급망·인프라
- 비밀: 환경변수/비밀 저장소만, 저장소 비밀 스캔(공개 전환 대비), 키 주기적 교체.
- 의존성 취약점 점검을 배포 전 자동화.
- 클라우드·호스팅: 위치(국가)·계약·백업·복구 목표 문서화. 금융권 망분리·클라우드 기준은 우리가 금융회사가 아니면 직접 적용되지 않으므로, **제휴사 요구 수준을 자료(13번) 기준으로 파악**.

### 3-6. 공급자 장애·종속
- 공급자 교체 구조(있음) 유지, 장애 시 사용자에게 보이는 동작(진행 중 단계 잠금·재시도 안내), 공급자 약관·가격 변경 감시.

### 3-7. 보안 시험 계획
- 상시(자동): 데이터 경계 테스트, 인젝션 시험 세트, 금지 표현 테스트, 권한 우회 테스트.
- 정기(분기 ⚠️): 모의 공격(인젝션·탈옥·시스템 프롬프트 노출), 의존성 점검.
- 출시 전/큰 변경 전: 외부 점검 검토.

### 3-8. 운영
- **사고 대응:** 탐지 기준, 유출 통지·신고 절차와 기한(법정 기한은 자료 2번으로 확인 🔲), 가족 구성원 개별 통지 문안, 연 1회 모의 훈련.
- **인증 로드맵:** ISMS-P 대상 여부 확인 → 필요하면 준비. 제휴(B2B) 때 요구되는 보안 점검(금융보안원 기준) 사전 점검.
- 감사 로그: 접근·동의·삭제·AI 호출 기록을 일정 기간 보관(개인정보 없이).
