## 1. 계산 규칙 (월 단위)

출발 시점을 0개월로 두고 1개월씩 진행한다. **목표 풀(goal pool)** 하나와, 순자산 계산용 **보조 계정**들을 따로 둔다.

매달 m(1 ≤ m ≤ horizon_months)에 대해:

1. **이자:** 목표 풀 잔액이 0보다 크면 `잔액 × (1 + 기대수익률/12)`. 0 이하면 이자를 붙이지 않는다(마이너스 잔액에 대출 이자를 붙이지 않는 단순화).
2. **현금흐름:** 이번 달에 유효한 현금흐름 항목을 모두 더한다(소득 +, 지출 −, 자녀 지원 +/− 등). 이벤트 항목(육아휴직 소득 감소, 병원비 증가)은 유효 기간 안에서만 더한다.
3. **일시금:** 이번 달에 해당하는 일시금을 더한다(작은 집으로 옮기고 남는 돈 등).
4. **목표 판정:** 목표 유형에 따라 처음으로 조건을 만족한 달을 기록한다.
5. **보조 계정 갱신:** 주택 가치, 대출 잔액, 주택연금 누적 잔액 등(순자산용). **목표 풀에는 영향을 주지 않는다.**

이 규칙은 v3 프로토타입의 `simulate()`와 같다. 그래서 기획안 숫자가 그대로 나온다(5절 수용 테스트).

### 목표 유형
| type | 판정 | 결과 지표 |
|---|---|---|
| `reach_target` | 목표 풀 ≥ target_amount 인 첫 달 | 목표 달성 시점(신혼부부: 집 살 돈이 모이는 때) |
| `runway` | 목표 풀 < 0 인 첫 달 | 예금으로 지낼 수 있는 기간(노인 가족). 끝까지 없으면 "horizon 이상" |

## 2. 입력 스키마

```jsonc
{
  "scenario_id": "newly",
  "horizon_months": 96,
  "start": {
    "goal_pool": 14000,                       // 우리 돈(만원)
    "pool_label": "우리 돈",
    "aux_accounts": []                         // 순자산용(선택). 신혼부부는 "우리 돈"에 보증금 중 우리 돈이
                                               // 이미 들어 있어 보조 계정이 없다(넣으면 이중 계산).
                                               // 노인 가족 예: {"id":"home","kind":"asset","value":55000}
  },
  "goal": {"type": "reach_target", "target_amount": 30000, "label": "집 살 때 필요한 우리 돈 3억"},
  "member_context": {"base_age": null},        // 노인 가족은 {"base_age": 72, "member_id": "m0"}
```

`Option` (LLM 역할 5가 만든다. `03_데이터모델.md`와 같은 구조)
```jsonc

    {"label": "둘이 버는 돈", "amount": 700, "category": "income"},
    {"label": "생활비", "amount": -350, "category": "expense"},

  ],
  "expected_return": 3.8,                          // %/년, 목표 풀 전체에 적용

  "volatility": 4.5,                               // %/년, 범위(보조) 계산용
  "events": [{"label": "육아휴직", "from_month": 20, "to_month": 31, "monthly_delta": -150, "category": "income"}],
  "lump_sums": [],

```

### 입력 검사 (엔진이 거부하는 값)
LLM이 이상한 조건을 내도 엔진이 멈추거나 터무니없는 숫자를 내지 않게 한다.
| 항목 | 허용 범위 |
|---|---|
| horizon_months | 1 ~ 360 |
| expected_return | 0 ~ 12 |
| volatility | 0 ~ 30 |
| 현금흐름 항목 1개 | −2,000 ~ 2,000 /월 |
| events, lump_sums | 각 10개 이하, 달 번호는 1 ~ horizon |
| 일시금 1개 | −100,000 ~ 100,000 |

거부 시 `{"error": {"field", "reason"}}`를 돌려준다. LLM tool 호출이면 이 메시지를 LLM에 되돌려 조건을 고치게 한다(`05_AI역할과_검증.md` 역할 5).

## 3. 출력 스키마

아래 숫자 중 `goal_hit_month`, `goal_hit_years`, `yearly` 1행은 재현값이고, 나머지(`end_pool`, `monthly` 행, `range`)는 형식을 보여 주는 예시값이다.

```jsonc
{
  "run_id": "run_…",                 // 입력 해시 + 엔진 버전
  "engine_version": "0.1.0",
  "results": [{
    "option_id": "B",
    "goal_hit_month": 59,             // 없으면 null
    "goal_hit_years": 4.92,
    "end_pool": 43031,
    "min_pool": 14279.3,              // 달마다 끝의 예금 중 가장 적은 값(2026-11-10, 노후처럼 'N년 이상'으로 같은 방법 구분)
    "min_pool_month": 1,              // 그 달
    "monthly": [                      // 미래 현금흐름 (기획안 12쪽)
      {"m": 1, "start": 14000, "interest": 44.3, "inflow": 700, "outflow": -465, "lump": 0, "end": 14279.3}
    ],
    "yearly": [{"year": 1, "start": 14000, "net_flow": 2820, "interest": 591, "end": 17411}],
    "net_worth": [{"m": 0, "value": 14000}, …],   // 순자산 = 목표 풀 + 보조 자산 − 보조 부채 (기획안 12쪽)
    "range": {                         // 보조 정보(✅ 기본 표시는 값 하나)
      "p10_hit_month": 55, "p50_hit_month": 59, "p90_hit_month": 64,
      "prob_within": {"months": 60, "value": 0.58},
      "seed": 1017, "paths": 1000
    },
    "basis": [                         // 화면 "이렇게 계산했어요" 표의 원천
      {"key": "start", "label": "보유 자산", "value": 14000, "source": "financial_snapshot"},
      {"key": "monthly_flow", "label": "매달 모이는 돈", "value": 235, "detail": "700 − 350 − 40 − 75", "source": "option"},
      {"key": "return", "label": "수익률", "value": 3.8, "source": "assumption:mix_deposit90"},
      {"key": "event:육아휴직", "label": "육아휴직", "value": -150, "detail": "20~31개월째", "source": "assumption"},
      {"key": "goal", "label": "가족이 정한 목표", "value": 30000, "source": "goal_setting"}
    ],
    "facts": [                         // 검증 구조가 쓰는 숫자 목록 (07 문서)
      {"fact_id": "B.goal_hit_years", "value": 4.92, "display": "약 4.9년", "unit": "year"},
```

## 4. 범위 계산 (보조 정보, ✅ 기본은 값 하나)

- 매달 수익률을 `정규분포(평균 r/12, 표준편차 volatility/√12)`에서 뽑아 같은 규칙으로 1,000번 계산한다. 시드는 옵션별로 고정한다(시연 재현).
- 결과: 달성 월의 p10 / p50 / p90, 정해진 기한(신혼부부 60개월) 안 달성 비율.
- 화면 표시: "운이 좋으면 / 보통이면 / 운이 나쁘면", "5년 안에 모일 가능성". 기본 값(결정론 계산)과 p50은 조금 다를 수 있으므로, 화면에는 **결정론 값을 주 숫자**로 쓰고 범위는 펼쳐 보기로 둔다(⚠️ 제안).
- 노인 가족: 예금 바닥 시점의 범위, "끝까지 남을 가능성".

## 6. 순자산 보조 계정 (기획안 12쪽 "대출 상환과 투자 배분에 따른 변화")

목표 풀 계산(=기획안 숫자)을 바꾸지 않으면서 순자산을 보여 주기 위한 부분이다.

| 계정 | 규칙 | 쓰는 곳 |
|---|---|---|
| (신혼부부) | 보증금 중 우리 돈이 목표 풀에 이미 포함돼 있어 보조 계정을 두지 않는다. 순자산 = 목표 풀 | 신혼부부 순자산 |
| 주택(자가) | 가치 상승률 가정(기본 0%) | 노인 가족 |
| 주택연금 누적 잔액 | 매달 지급액 + 이자(가정) 누적. 집 가치에서 뺀 값이 "물려줄 몫" | 노인 가족 B안: "끝까지 사시고, 물려줄 몫은 줄어요"를 숫자로 |
| 집 교체 | 매도가 − 매수가 − 비용 = 일시금(목표 풀로 들어감), 주택 가치 교체 | 노인 가족 C안 |

🔲 주택연금 이자율·지급액, 이사 비용은 가정값(04 문서 3절)으로 둔다.

## 7. 재점검(지속관리) 계산

`compare(run_before, run_after)` → 달라진 입력 목록, 목표 달성 시점 차이(개월), 끝 금액 차이, 순자산 차이. 가족 홈의 "지난 합의와의 차이"(기획안 15쪽)에 쓴다. 예: 예금 금리 가정이 0.5%p 내리면 달성 시점이 몇 개월 늦어지는지.

## 정책 계산(2026-11-10)

계산할 때는 계산엔진만 쓴다(CLAUDE.md 5절). 계산에 필요한 표·비율은 엔진 데이터 `data/assumptions.json`에 미리 둔다.

| 계산 | 함수 | 데이터 |
|---|---|---|
| 주택연금 월 수령액(부부 중 젊은 사람 나이·집 시세, 칸 사이 직선 보간 추정) | `engine/policies.py reverse_mortgage_monthly`, `reverse_mortgage_age` | `reverse_mortgage.monthly_table`(공사 월지급금 예시표, 원문 인용·줄 대조 테스트) |
| 집 팔고 작은 집으로: 남는 돈·새 집 시세 | `engine/policies.py sell_home` | `sell_home.cost_ratio`, `new_home_ratios` |
| 상품 비교: 우대 합산(묶음은 상한까지, 단계형·택일은 큰 것), 내가 받을 금리 = 기본 + 우대(공시 최고 우대폭·원문 상한 안) | `engine/rates.py reachable·applicable·my_rate` | 우대 항목은 온톨로지(`ontology/conditions.py`)가 원문에서 만들고 해당 여부를 판정 |
| 통계 기준(내 집 마련): 정책대출 LTV로 직접 마련할 돈, 1주택 취득세(6억 이하 1%, 9억 초과 3%, 그 사이는 금액 없음) | `engine/policies.py own_money_with_ltv·acquisition_tax` | `home_purchase.ltv`, `home_purchase.acquisition_tax`(원문 인용, 2026-11-11) |

자격 판정(주택연금 55세·집 등)은 온톨로지가 하고, 판정이 '해당 안 됨'이면 그 정책은 방법에 넣지 않는다. 요청 조립(`llm/plan.py`)은 엔진 함수의 결과를 요청에 담기만 한다.

2026-11-11 우대금리 합산·통계 기준 계산도 옮겨, 화면에 보이는 계산 숫자는 모두 계산엔진에서 나온다(옮기기 전후 결과 동일 대조).
