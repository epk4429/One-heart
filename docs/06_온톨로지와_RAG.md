# 06. 온톨로지와 RAG

> 이 서비스의 금융 지식 계층(온톨로지·RAG)이 **무엇이고, 어느 단계에서, 왜 쓰이는지**를 한 문서로 정리한다(2026-11-08 파일럿 기준으로 다시 씀).

> 할 일은 `00_할일.md`에만 적는다.

## 0. 한 장 요약

| | 온톨로지 | RAG |
|---|---|---|
| 한 줄 정의 | 금융 지식을 **"무엇이 무엇과 어떤 관계인지"** 정해진 칸과 규칙으로 정리한 지도 | 원문 더미에서 **관련 부분을 찾아 꺼내 오는** 장치 |
| 맡은 일 | **판단·숫자**: 이 약속엔 어떤 상품·제도가 맞나, 이 가족이 자격이 되나, 어느 상품이 목표에 더 맞나, 미래 계산의 기준값 | **설명·근거**: AI 제안의 근거가 되는 공식 원문, 관련 법령 원문 |
| 답을 정하는 쪽 | **코드(규칙)**. AI는 약속 문장을 어휘 ID로 바꾸는 일만 한다 | **검색 코드**가 조각을 고르고, 원문을 **바꾸지 않고** 보여 준다. AI가 인용하면 서버가 글자 일치를 검사한다 |
| 자료 | 금감원 공시 상품 2,070개, 제도 8개, 어휘(필요 16·제약 7·상품 유형 21) | 법령 7개(조각 279), 금감원 금융꿀팁 18편(조각 110) |
| 위치 | `ontology/` | `rag/`, `knowledge/rag/chunks.jsonl` |

**원칙 다섯 가지**
1. **AI는 금융 사실을 기억으로 말하지 않는다.** 상품·제도·숫자는 온톨로지(규칙)·엔진(계산)·원문(RAG)에서만 나온다.
2. **판정·숫자는 온톨로지, 설명·근거는 RAG.** 자격·금리·한도 판정에 RAG 검색 결과를 쓰지 않는다.
3. **둘은 서로 참조하지 않는다.** 서버가 ID로 고르고 검사하는 자료는 온톨로지, 원문을 찾아 보여 주는 자료는 RAG다. 한 원문을 양쪽에 쓰지 않는다(제도 안내문은 온톨로지 규칙의 출처로만, 2026-11-04 형님 결정).
4. **실제 상품·금융회사 이름은 상품 추천(조건 비교) 화면에서만** 나온다. 앞 단계 AI 출력에 이름이 나오면 서버가 막는다(G12).
5. **검토자가 없으니 기계로 검사한다.** 인용 글자 일치, 숫자 일치, 독립 정답 대조, 일부러 고장 낸 데이터로 검사가 실제로 잡는지 확인.

## 1. 파일럿 범위: 무엇을 쓰고 무엇을 두나

파일럿 대상은 **신혼부부**와 **노후 준비 가족** 두 유형이다(2026-11-08 형님 결정). 참가자는 지인이고 자기 가족 정보를 조금 바꿔 넣으므로, 두 유형 안에서는 **어떤 가족이 와도** 동작해야 한다. 온톨로지는 가족별 코드가 아니라 데이터 지도라서, 두 유형은 그중 자기에게 해당하는 길만 지나간다.

**결론: 다른 유형까지 고려해 만든 부분은 지우지 않고 둔다.** 서로 얽혀 있어(그래프·검증 묶음·테스트) 떼면 깨질 수 있고, 남겨 둬도 비용이 거의 없다. 파일럿에서 쓰지 않는 부분은 **화면에서 감추고**(2026-11-08 형님 결정, `00_할일.md`), 검증·개선은 두 유형에만 집중한다.

| 구분 | 신혼부부가 주로 지나가는 길 | 노후 준비 가족이 주로 지나가는 길 | 두 유형에서 드문 길(감추지 않음, 2026-11-09 형님 결정) / 감춘 것 |
|---|---|---|---|
| 필요 | 집 살 때 자격·한도 확인, 육아휴직 준비금, 여윳돈 투자 비중, 함께 내는 돈 기록, 아이 보장, 전세 보증금, 자녀 교육비 | 집에 살며 생활비, 병원비 통장, 간병비, 재산 나누기(상담), 은퇴 뒤 매달 쓸 돈 | 사업 자금 |
| 두 유형 공통 필요 | 목돈 함께 모으기, 비상금, 대출 계획대로 갚기 | ← 같음 | |
| 제도 8개 | 디딤돌·신생아 특례 디딤돌·보금자리론·버팀목·신생아 특례 버팀목·주택청약 | 주택연금·기초연금 | 없음(8개 모두 해당) |
| 실제 상품 범주 | 적금·정기예금·주택담보대출·전세자금대출 | 적금·정기예금(·주택담보대출) | 개인신용대출(공시에 한도·수수료가 없어 '확인 필요' 안내, 데이터는 나중에 조사), 개인사업자대출 — 가족 정보에 해당 대출이 있거나 약속에 사업 자금이 있을 때만 나옴 |
| 그 밖 | | | **감춤**: 공유 노드 그래프 화면 링크(`/graph.html`은 남김, `web/js/config.js HIDE`). 검증 묶음의 다른 가구 유형(한부모·자영업 등, 회귀 확인용으로만 유지) |

### 2.3 왜 하나로 합치지 않고 둘로 나눴나

| 하나로 합쳤다면 | 둘로 나눈 지금 |
|---|---|
| AI가 원문을 읽고 판정까지 → 해석 실수가 그대로 결과가 됨 | 판정은 원문을 읽고 만든 규칙 + 정답 테스트 |
| 검색이 엉뚱한 조각을 가져오면 판정도 틀림 | 검색 실수는 설명 화면에만 영향, 판정은 그대로 |
| AI가 법·제도 문장을 바꿔 말하다 뜻이 달라짐 | RAG는 원문을 그대로 보여 주고, AI 인용은 글자 일치 검사 |

## 3. 온톨로지

### 3.1 모양: 주축은 실제 상품, "필요"는 가족과 상품을 잇는 다리

- **데이터의 주축 = 실제 상품**(형님 결정). 공시 상품 2,070개가 하나하나 노드이고, 여러 상품·제도가 함께 가진 항목(금융회사, 범주, 가입 방법, 우대 종류, 나이·무주택 같은 사람 조건, 원문)은 **공유 노드**로 묶인다(3.8절).
- **서비스가 상품에 닿는 길 = 필요.** 가족은 상품이 아니라 약속을 말하므로, 약속 → 필요 → 상품 유형 → 실제 상품·제도로 내려간다. 필요를 따로 두는 이유: 출발점이 가족의 말이고, 상품이 없는 필요(주택연금·기초연금은 제도, 상속은 상담, 투자 비중은 가족이 직접)도 있고, 앞 단계는 상품 이름을 쓰면 안 되기 때문이다.

```
                         [합의안의 약속]  ← 가족이 정한 문장
                                │  AI(역할 8)가 어휘 ID로 바꿈(목록 밖 ID는 서버가 거부)
              constrainedBy     │ requires
     [제약 7개] ◄───────────────┤
          │                     ▼
          │               [필요 16개] (다리)
          │ 규칙으로 거름        │ satisfiedBy
          └──────────────────► ▼
                        [상품 유형 21개]  ← 속성: 위험도·기간·유동성·세제·가입조건
                                │
        ┌───────────────────────┼─────────────────────────┐
        ▼ real                  ▼ program                 ▼ none / consult / self
 [실제 상품 2,070개]       [공적 제도 8개]           [데이터 없음·상담·직접]
  금감원 공시 6범주         자격 규칙 + 원문 인용       이유만 보여 줌
        │                       │
 [우대·한도 규칙]                │
        └──────────┬────────────┘
                   ▼
   [원문 저장소 knowledge/sources/: 공시 원본·제도 안내문]  ← 모든 노드의 근거(sha256)
```

### 3.2 뼈대: 노드와 관계

| 구성 요소 | 개수 | 예 | 파일 |
|---|---|---|---|
| 약속 | 합의안마다 | "휴직 준비금은 주식에 넣지 않고 따로 둬요" | 합의안(역할 7) |
| 필요 | 16 | `N_leave_fund` 육아휴직 동안 쓸 돈 따로 모으기 | `ontology/vocab.json` |
| 제약 | 7 | `C_principal_protected` 원금이 줄면 안 돼요 | `ontology/vocab.json` |
| 상품 유형 | 21 | `P_installment_savings` 적금(원금 보장) | `ontology/product_types.json` |
| 제약 → 속성 규칙 | 7 | 원금 보장 → `risk`가 "원금보장"이어야 통과 | `ontology/rules.json` |
| 실제 상품 / 제도 | 2,070 / 8 | 공시 적금 / 버팀목 전세대출 | 3.5·3.7절 |

관계: `약속 —requires→ 필요`, `약속 —constrainedBy→ 제약`, `필요 —satisfiedBy→ 상품 유형`, `상품 유형 —hasAttribute→ 속성`.

가족 상황 조건: 필요(예: 주택연금 = 집이 있고 55세 이상)와 **상품 유형**(2026-11-10부터, 예: 연금저축 = 노후 생활비의 주인이 이미 은퇴했으면 연결하지 않음. 주인은 목표의 '누구 기준' 구성원, 없으면 가족 전체. 은퇴 여부는 가족방 만들기에서 가족이 고른 '지금 하는 일'로만 보고 모르면 판단하지 않음)이 `requires`를 가질 수 있고, 맞지 않으면 코드가 연결하지 않으며 상품 유형은 카드의 '제외'에 이유를 남긴다(임의결정 69).

| 재산 나누는 방법 정하기 | 가족 신탁 상담(상담) |
| 목표 금액 함께 모으기 | 적금·정기예금(실제), 혼합형 투자·모임통장(데이터 없음) |
| 비상금 따로 두기 | 수시입출금(데이터 없음), 적금(실제) |
| 대출 계획대로 빨리 갚기 | 미리 갚기 계획(직접), 갈아타기 상담(상담), 주택담보대출·개인신용대출(실제) |
| 자녀 교육비 미리 모으기 | 적금(실제), 혼합형 투자(데이터 없음) |
| 은퇴 뒤 매달 쓸 돈 | 연금저축(데이터 없음), 주택연금·기초연금(제도) |

**제약 7개:** 원금이 줄면 안 돼요 / 정해진 때(출산 등)까지 모아야 해요 / 필요할 때 바로 꺼내야 해요 / 지금 집에 계속 살아야 해요 / 투자 비중은 20%까지예요 / 가족이 함께 확인할 수 있어야 해요 / 상속·세무·법률은 전문가 상담으로 연결해요.

### 3.3 AI와 코드의 분업 (역할 8 → 탐색 코드)

```
합의안의 약속 문장 ──[역할 8: AI]──→ {약속 c2: 필요 N_leave_fund, 제약 C_principal_protected}
                                       │  서버 검사: 어휘 목록에 있는 ID만
                                       │  가족 상황 검사: 조건이 붙은 필요는 가족 상황이 맞을 때만 남김
                                       ▼
                           [ontology/search.py: 코드]
                           필요 → 후보 유형 → 제약 규칙 통과? → 통과한 유형 + 제외 사유 + 경로
```

- AI는 약속을 어휘 ID로 바꾸기만 한다. 상품은 고르지 않는다. 맞는 필요가 없으면 비워 둔다.
- 조건이 붙은 필요는 코드가 가족 정보로 한 번 더 막는다(`llm/pipeline.py recommend`). 예: "지금 집에 살면서 생활비"는 집이 있고 55세 이상인 가족이 있을 때만.
- 꼭 지켜야 하는 돈(휴직 준비금·비상금·병원비) 필요에는 AI가 빠뜨려도 "원금이 줄면 안 돼요"를 코드가 붙인다(`vocab.json` `default_constraints`).

**예(신혼부부):** 약속 "휴직 준비금은 주식에 넣지 않고 따로 둬요" → 필요 `N_leave_fund` + 제약 원금 보장 → 적금(통과, 실제 공시 적금을 목표 적합도 순으로), 수시입출금(통과, 데이터 없음), 혼합형 투자(**제외: 원금 보장이 아니라서**). 화면 "왜 이 상품인가요"에 이 경로가 그대로 나온다.

### 3.4 필요마다 "갈 수 있는 길" (routes)

모든 필요에 길이 하나 이상 명시돼 있어야 한다(`tests/test_routes.py`). 맞는 상품이 없으면 "없어요", 데이터가 없으면 "데이터가 없어요"를 이유와 함께 보여 준다.

| 길 | 뜻 | 해당 유형 |
|---|---|---|
| real | 금감원 공시 실제 상품 비교 | 적금, 정기예금, 주택담보대출, 전세자금대출, (개인신용대출, 개인사업자대출) |
| program | 공적 제도(원문 규칙으로 판정) | 주택청약, 첫집 정책대출, 정책 전세대출, 주택연금, 기초연금 |
| none | 상품은 있지만 공시 API에 없음 | 혼합형 투자, 모임통장, 어린이 보험, 간병 보험, 수시입출금, 연금저축 |
| consult | 상담 연결 | 가족 신탁 상담, 대출 갈아타기 상담 |
| self | 가족이 직접 지킴 | 집 줄여 이사, 대출 미리 갚기 계획, 여윳돈 투자 비중 |

코드: `ontology/routes.py`, 화면 설정 `/api/config`의 `need_routes`.

### 3.5 실제 상품 층

- **수집(`tools/fetch_finlife.py`):** 금감원 "금융상품 한눈에" 오픈 API 6개 범주 × 권역 전체, 공시월 2026-10. 정기예금 436, 적금 337, 주담대 112, 전세대출 58, 신용대출 115, 사업자대출 1,012 = 2,070개. 응답은 손대지 않고 페이지별로 sha256과 함께 보관. 연금저축 API는 응답이 비정상이라 뺐다(부록 A).
- **상품 노드(`tools/build_products.py` → `ontology/products/*.json`):** 숫자 칸으로 공시된 정형 항목은 그대로 옮기고, 글로 공시된 항목(우대조건·가입대상·한도)은 원문을 두고 규칙으로 바꾼다.
- **우대·가입 규칙(`ontology/conditions.py`, 예금·적금 773개):** 우대 글을 줄 단위로 나눠 금액·종류·묶음(상한·택일·단계형)을 뽑는다. 종류는 action(하면 받음: 급여이체 등) / attribute(사람 조건: 나이·자녀 수 등) / relation(거래 관계: 신규고객 등).
  - **계산은 계산엔진(2026-11-11):** 온톨로지는 우대 글을 항목(금액·종류·묶음 구조)으로 만들고 가족에게 해당하는지 판정만 한다. 항목을 더하는 규칙(묶음 상한·단계형·택일)과 '내가 받을 금리'는 `engine/rates.py`가 계산한다.
  - **독립 대조:** 뽑은 우대 합계를 공시의 "최고 우대금리 − 기본금리"와 비교한다. 상태: verified 635 / capped 6(공시를 상한으로) / needs_check 132(화면에 "확인 필요").
- **대출(`ontology/loans.py`):** 한도 글 → 비율·최대 금액, 중도상환수수료 글 → 요율·면제 기간.
- **범주 통계(`ontology/category_stats.json`):** 범주·기간별 금리의 최저·중간·최고. 상품 이름 없이 앞 단계에 쓸 수 있는 유일한 상품 지식이다.

### 3.6 목표 적합도 비교 (`ontology/fit.py`, `/api/products/fit`)

"금리 높은 순"이 아니라 **"이 가족의 목표에 맞는 순"**으로 줄 세운다. 화면 문구는 "우리 목표에 잘 맞는 순서예요"(추천이라고 쓰지 않음).

| | 저축형(적금·정기예금) | 대출형(주담대·전세) |
|---|---|---|
| 비교 값 | 만기 **세후** 이자(15.4%) | 기간 전체 **총 비용**(이자+수수료) |
| 순서 | 넣을 돈이 한도 안인지 → 가입할 수 있는지 → 세후 이자(1만원 단위로 묶음) → 확인 필요 적은지 → 할 일 수 | 빌릴 돈이 한도 안인지 → 받을 수 있는지 → 총 비용(10만원 단위) → 확인 필요 적은지 → 금리 |
| 계산 | `engine/product_math.py` | 같은 엔진(원리금균등·원금균등·만기일시·일찍 갚기) |

사람 조건 판정은 세 값이다: **met**(확실히 맞음 → 금리에 넣음·통과) / **not_met**(확실히 아님 → 빼고 사유 표시) / **unknown**(모름 → 짐작하지 않고 "해당되면 +x%p"). 대출은 만 19세 이상 이름으로만 비교한다.

### 3.7 제도 규칙 (`ontology/programs.json`, `programs.py`)

- 제도 8개: 주택연금, 디딤돌, 신생아 특례 디딤돌, 보금자리론, 버팀목, 신생아 특례 버팀목, 주택청약종합저축, 기초연금.
- 만드는 법: 공식 안내 페이지를 원문 저장소에 보관 → Claude Code가 원문을 읽고 조건·숫자를 적음 → **모든 항목에 원문 인용** → 테스트가 인용 글자 일치·숫자 포함을 검사.
- 규칙 모양: `eligibility`(가족 정보로 판정하는 조건 + 인용), `unmodeled`(기관이 확인하는 조건, 늘 따로 표시), `terms`(금리·한도·기간 + 인용).
- 판정: 확실한 값(나이·집 수)은 met/not_met, 추정 값(연소득 = 월 수입 × 12 등)은 unknown + 방향("추정하면 기준 안이에요 / 넘어요"). 여러 세대 가족방은 세대원 무주택·부부합산 소득을 확인 필요로.
- 화면 문구: "기본 조건은 맞아요(기관 심사 조건은 확인 필요) / 지금은 해당하지 않아요 / 확인이 필요해요".
- **계산엔진과의 경계(2026-11-10 고침):** 온톨로지는 주택연금 **자격 판정까지만** 한다(판정이 '해당 안 됨'이면 미래 계산에 주택연금 방법을 내지 않음). **월 수령액은 계산엔진이** 엔진 데이터(`data/assumptions.json` reverse_mortgage.monthly_table, 공사 월지급금 예시표·원문 인용)로 계산한다(`engine/policies.py`, 칸 사이는 직선 보간 '추정'). 공식 예시 '70세·3억 → 월 약 92만 3천원'과 표의 줄이 원문과 같은지는 테스트로 확인. 7단계 제도 카드의 '예상 월지급금'도 서버가 계산엔진에서 받아 붙인다. 예전에는 표와 계산이 온톨로지에 있었다(역할 침범).

### 3.8 공유 노드 그래프 (`ontology/graph.py`, `/graph.html`)

흩어진 온톨로지 데이터를 노드·관계 하나의 그래프로 묶어 보여 준다(새 사실을 만들지 않음, 판정은 `fit.py`·`programs.py`). 노드 약 2,850개·관계 약 11,000개. 예: "무주택" 노드 하나에 무주택 전용 적금과 정책대출 4개가 함께 이어진다. 파일럿에서는 설명용이고 참가자 화면에서는 감춘다.

## 4. RAG (`rag/index.py`, `llm/evidence.py`)

### 4.1 원문과 조각

| 묶음 | 원문 | 조각 | 쓰는 곳 |
|---|---|---|---|
| 법령 | 국가법령정보센터 본문 7개(기초연금법, 한국주택금융공사법·시행령, 주택도시기금법, 주택공급에 관한 규칙, 예금자보호법, 조세특례제한법 중 제87조·제88조의2) | 조문(긴 조문은 항) 단위 279개, 부칙 제외 | 화면 7 "관련 법령 찾아보기" |
| 금융꿀팁 | 금감원 "금융꿀팁 200선" 18편(첨부 한글 파일 본문) | □ 절 단위 110개, 보도자료 머리표 제외 | 화면 4 제안 근거, 화면 5 방법 근거 |

- 조각 글은 원문의 연속된 줄 그대로다(바꿔 쓰지 않음, 테스트로 확인). 출처는 허용 목록 도메인만(G1), 원문은 sha256과 함께(G2).
- 조각에 온톨로지 ID를 붙이지 않는다. 법령마다 색인할 조문 범위는 RAG 안의 `LAW_SCOPE`가 정한다.

### 4.2 검색

- **BM25 + 글자 2-gram:** 한국어 조사("대출은/대출을") 때문에 두 글자씩 비교한다. 문서가 수백 조각이라 벡터 검색 없이 충분하고, Anthropic에는 임베딩 API가 없다.
- 보강: 말끝·조사 떼기, 비슷한 말(나이→연령 등), 제목 가중치. 질문 낱말 절반 이상이 들어간 조각만 내놓고, 없으면 "찾지 못했어요".
- 법령과 꿀팁은 BM25 통계를 따로 계산한다.

### 4.3 AI 근거 대기 (공동 목표 제안 4a·4c, 방법 설계 5)

1. 코드가 가족 정보(확인된 요약·동의한 기준·목표 종류, 대출·전세·투자·나이)로 꿀팁 조각을 찾아 AI에 준다(조각 ID·출처 제목·글). 모든 가족에게 같은 조각을 주는 고정 목록은 없다.
2. AI는 받은 조각 안에서만 근거를 대고, 근거마다 조각 글에서 그대로 복사한 인용을 단다. 맞는 조각이 없으면 인용하지 않아도 된다(억지 인용 금지).
3. 서버가 조각 ID가 준 것인지, 인용이 원문에 글자 그대로 있는지 검사하고, 어기면 다시 쓰게 한다(G11). 금융회사·상품 이름도 함께 검사(G12).
4. 화면: 근거 문구가 점선 밑줄 버튼이 되고, 누르면 인용 원문·자료 이름·작성일이 그 자리에서 보인다(형님 결정: 근거는 "~이니까"로 문장 안에).

### 4.4 법령 찾아보기 (화면 7)

제도 판정 카드마다 주제 버튼(누가 받을 수 있나요 / 얼마까지 / 금리·비용 / 중간에 갚거나 그만두면 / 주의할 점 / 어디서 신청) + 직접 입력, 예적금 비교 아래 "예금자보호·비과세 법령 찾아보기". 결과는 **AI 요약 없이 원문 그대로**, 기관·시행일·수집일·원문 링크. API `/api/rag/search`.

**AI가 RAG로 직접 답하지 않는 이유:** 법·제도 문장은 바꿔 말하다 뜻이 달라지기 쉽고 검토자가 없다. 원문을 그대로 보여 주는 것이 가장 안전하다. 인용 검사 함수(`check_citation`)는 준비돼 있다.

| 검증 묶음 | 다양한 가족에서 잘못 노출·부당 제외 | `python -m ontology.kb_eval`(가상 가족 12곳, 오류 지표 0) |

- 검증 묶음의 정답은 판정 코드와 따로 만든다(제도는 사람이 원문을 읽고 적음, 상품은 다른 엄격한 패턴으로 원문을 다시 읽음). 고친 코드를 일부러 되돌려 검사가 잡는지도 확인했다(돌연변이 확인).
- **파일럿 기준 검증:** 가상 가족 12곳 중 신혼부부·노후 준비 계열(신혼 전세, 영유아, 은퇴 직전, 고령 부부, 고가 주택 고령 부부, 3대 가족, 경계 나이)을 주 지표로 보고, 나머지는 회귀 확인용으로만 돌린다. 두 유형의 변형 가족을 더 만드는 일은 `00_할일.md`.
- 인용 글자 일치는 "원문에 그 글이 있다"까지만 보증하고, "원문을 올바르게 해석했다"나 "인용이 주장을 뒷받침한다"는 보증하지 못한다. 그래서 해석이 끼는 조건은 확인 필요로 떨어뜨린다.

## 8. 설명용 예상 질문과 답

**Q. 그냥 ChatGPT에 물어보면 되지 않나요?** AI는 금리·자격 기준을 기억으로 말하다 틀릴 수 있고 이유를 설명하지 못합니다. ONE-Heart는 공식 원문으로 만든 규칙으로 판정하고, AI는 가족의 말을 정해진 어휘로 바꾸는 일만 합니다. 같은 가족이면 늘 같은 답이 나오고 "약속 → 필요 → 상품 유형" 경로로 이유를 보여 줍니다.

**Q. 상품을 추천하나요?** 아닙니다. 합의한 목표·조건에 맞는지를 규칙으로 비교해 정보를 보여 주고, 선택과 가입은 가족이 합니다. 실제 상품 이름은 이 비교 화면에서만 나옵니다.

**Q. 데이터가 정확한지 누가 확인하나요?** 기계 검사입니다. 모든 규칙에 원문 인용을 붙여 글자 일치를 검사하고, 우대금리는 금융회사가 따로 낸 공시 숫자와 대조하며, 가상 가족으로 잘못 노출·부당 제외가 0인지 확인합니다.

**Q. AI가 근거를 지어내지 않나요?** AI는 서버가 준 원문 조각 안에서만 근거를 대고, 인용이 원문에 글자 그대로 있는지 서버가 검사합니다. 어기면 화면에 나가지 않습니다.

## 부록 A. 데이터 이상 기록 (확인 대기)

수집·정리하다 발견한 이상한 점이다. "무엇이 이상한가 → 지금 처리 → 확인할 것" 순서. 확인하는 일 자체는 `00_할일.md`에 있다.

**금감원 공시 API**
- **연금저축 API 응답 이상:** `annuitySavingProductsSearch`가 건수와 목록이 맞지 않고(보험 권역 46건이라면서 4건, 그것도 대출 상품) 연금 항목이 없다. 안내 페이지의 요청 주소는 적금과 같은 이름으로 잘못 적혀 있다. → 수집에서 뺐고 연금 항목이 없는 응답은 저장하지 않는다. → 일시 장애인지, 다른 공식 출처(통합연금포털 등)가 있는지.
- **상품 코드 겹침:** 저축은행 3건(하나·진주·아산)이 예금과 적금에 같은 코드를 쓰고, 진주·아산은 적금 목록에 '정기예금' 이름이 들어 있다. 아이엠뱅크 신용대출 `WR0002F`에 두 종류가 함께 있다. → ID를 `PRD_<범주>_<회사>_<상품>(_<종류>)`로 구분. → 공시 오류인지.
- **대출 공시의 빈 항목:** 신용대출은 한도·수수료 항목이 없음(모두 확인 필요), 사업자대출은 신용점수 구간 금리가 빈 상품이 많음(평균·중간값으로 계산하고 표시), 주담대·전세는 지난달 평균이 빈 옵션이 있음.
- **금융투자 권역:** 회사 개요 공시월이 2020~2021년으로 오래됐고, 6개 범주 상품이 0건이다.

**공식 안내 페이지·제도**
- 고용24(육아휴직급여)는 스크립트 화면이라 원문을 자동 보관할 수 없었다.
- 보금자리론 금리는 매달 바뀌어 "금리는 매달 공사가 정해요"로만 보여 준다.
- 주택연금 월지급금 예시표는 55~80세(5세 간격) × 1~12억 칸만 있어 사이는 직선 보간 추정이다.
- 기초연금 소득인정액은 소득·재산 환산을 합친 값이라 늘 "확인 필요"에 방향만 표시한다.
- 비과세종합저축: 조세특례제한법 제88조의2 원문은 확인(65세 이상 기초연금 수급자, 1명당 5천만원)했지만 규칙화는 보류(형님 결정). → 2026-11-11 형님 결정으로 파일럿 전에 규칙화(`00_할일.md` 1-7의 4번)

**우대조건**
- 원문 우대가 있는데 공시 최고금리 = 기본금리인 상품 27개는 needs_check로 둔다.
- "다자녀" 기준이 은행마다 달라, 원문에 숫자가 없으면 3명 기준, 2명은 확인 필요.
- 우대조건 "없음"인데 공시 최고 우대금리가 기본보다 높은 상품(국민 KB Star 정기예금 +1.2%p, 신한 쏠편한 정기예금 +1.05%p, 하나의정기예금 +1.3%p), 원문 최고보다 공시가 높은 상품(신한 My플러스, 제주 J정기예금·스마일드림), 우대 금액이 원문에 없는 상품(케이뱅크 마이키즈 적금, 부산은행 적금 4개). → 공시 최고 우대금리에 이벤트·특판이 들어간 것인지. 전체 목록은 `ontology/conditions.json`의 `benefit_status: needs_check`.
- 저축은행 예금·적금 673개의 우대조건은 공시 숫자 대조만 거쳤고, 원문을 읽고 적은 정답 사례는 은행 상품 12개뿐이다.

**가족방**
- 1인 가구는 가족방을 만들 수 없다(구성원 2~6명). 파일럿 대상(신혼부부·노후 준비 가족)에는 영향 없음.
