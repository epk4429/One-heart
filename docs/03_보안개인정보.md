# 03. 보안·개인정보 설계

두 부분으로 나눈다(✅ 사용자 결정, CLAUDE.md 9절 "보안").

- **A. PoC에서 실제로 지키는 것** — 비용이 거의 없는 코딩 습관 + 공개 범위 선택(⚠️ 01 문서 범위 추천)
- **B. 실제 서비스의 보안 설계** — 심사 설명용. 구현하지 않는다

## A. PoC에서 지키는 것

### A-1. API 키는 서버리스 환경변수에만 (⚠️ 제안, 사용자 확인 대기)
- 프론트(GitHub Pages)에는 어떤 키도 두지 않는다. GitHub Pages 저장소는 공개라서 키가 한 번이라도 커밋되면 노출된다.
- `.env`는 `.gitignore` 처리 완료. 저장소에는 `.env.example`(키 이름만)만 둔다.
- 대상 키: `HF_TOKEN`(Hugging Face), `ANTHROPIC_API_KEY`, 공공 데이터 API 키(쓰는 경우).

### A-2. 데이터별 LLM 입력 경계 (⚠️ 제안 → 4절 1번 원칙을 구조로 지킴)
`02_데이터모델.md`의 공개 범위 표시로 LLM 역할마다 넣을 수 있는 데이터를 막는다.

| LLM 역할 | 넣을 수 있는 것 | 절대 넣지 않는 것 |
|---|---|---|
| 1 요약(개인) · 2 말뜻 재질문 | 해당 구성원의 대화 원문·재질문 기록 | 다른 구성원의 원문 |
| 1 요약(가족 이야기) | 방장이 쓴 이야기 | 대화 원문 |
| 3~8 공유 단계 | 확인된 요약, 공동 목표, 공개를 고른 금융 항목, 엔진 결과 | 대화 원문, 확인 전 요약, 숨긴 금융 항목의 개별 금액 |

구현: 역할별 "입력 조립 함수"가 공개 범위 표시를 보고 필드를 고른다. 프롬프트를 직접 문자열로 이어 붙이지 않는다. 테스트로 "공유 단계 프롬프트에 원문 대화 문장이 들어가지 않는다"를 확인한다.

### A-3. 공개 범위 본인 선택 (기획안 9·11쪽)
- 화면 2(우리 가족 이야기)에서 금융정보를 가져온 뒤, 구성원마다 항목별로 "공개 / 비공개"를 고른다.
- 계산엔진은 서버에서 전체 금액으로 계산한다(가족 전체 계획이므로). 화면과 LLM에는 A-2 규칙대로만 간다.
- 시연에서는 노인 가족 부모님의 예금을 "비공개"로 두는 장면이 자연스럽다(⚠️ 제안).

### A-4. 화면 출력 이스케이프 (⚠️ 제안)
LLM 출력과 사용자 입력은 화면에 넣기 전에 항상 이스케이프한다. 프로토타입의 `esc()` 함수를 공통 유틸로 쓴다.

### A-5. 문서로만 남기는 것 (✅ 사용자 결정: 구현하지 않음)
- 프롬프트 인젝션 방어(정상 흐름으로만 시연)
- 시연 암호, 호출 횟수 제한(요금은 나중에 API 토큰 제한으로 막음)
- 실제 정보 입력 경고 문구

## B. 실제 서비스의 보안·개인정보 설계 (심사 설명용, 구현 안 함)

### B-1. 금융정보 수집
- 마이데이터(본인신용정보관리업) 연계로 본인 동의 범위 안에서만 수집한다. 동의 항목·기간·철회를 화면에서 관리한다.
- 연동 경로: 금융위원회 허가를 받은 본인신용정보관리업자만 정보제공자(은행·카드·보험·증권 등)로부터 API로 데이터를 직접 받을 수 있다. 따라서 실서비스는 ① 직접 허가를 받거나(자본금·전산보안설비·임원 및 대주주 요건 심사, 금융보안원 API·보안 점검 통과) ② 이미 허가받은 사업자 또는 마이데이터 API 연동 기업과 제휴해 이용자가 동의한 정보를 받는 방식 중 하나로 연동한다. 초기에는 ②가 현실적이며, 제휴 시 제공 범위와 제3자 제공 가능 여부는 약관·법률 검토가 필요하다. 🔲 허가 요건의 세부 수치는 금융위원회·금융보안원 자료로 확인한다.
- 직접 입력은 본인 계정에서만 가능하다.
- 부모님 금융정보: 부모님 본인 인증과 동의가 있어야 연결된다. 🔲 자녀가 부모 정보를 **지속 열람**하는 구조의 동의 요건은 법률 검토가 필요하다(CLAUDE.md 7절).

### B-2. 저장과 접근 통제
- 대화 원문: 본인 키로 암호화해 저장, 본인만 복호화. 운영자도 원문을 볼 수 없게 설계한다.
- 요약과 원문은 분리 저장한다. 가족방에는 요약만 연결된다.
- 금융 원본은 구성원별로 저장하고, 공개 범위 설정에 따라 가족방에 보이는 형태(개별·합계·숨김)를 서버가 만든다.
- 합의안은 버전별로 저장하고, 서명은 버전 해시에 묶는다(위·변조 확인).

### B-3. LLM 공급자
- 입력 데이터를 학습에 쓰지 않는 계약(API 약관) 조건의 공급자만 쓴다. 보관 기간을 최소화한다.
- LLM에는 A-2 규칙대로 최소한의 데이터만 보낸다. 이름은 가명(구성원 A·B)으로 바꿔 보내고 화면에서 되돌린다.

### B-4. 데이터 최소화·삭제
- 가족방 해산 시 대화 원문·금융 원본을 삭제하고, 합의안은 본인 선택에 따라 보관한다.
- 지속관리에 필요한 최소 항목(목표·약속·이행 여부)만 장기 보관한다.

### B-5. 관련 법 (🔲 검토 필요 — 아래는 검토할 항목 목록이지 결론이 아니다)
| 법 | 검토할 지점 |
|---|---|
| 개인정보보호법 | 가족 구성원 간 정보 공유의 동의 방식, 민감정보(건강: 병원비·간병) 처리 |
| 신용정보법(마이데이터) | 본인신용정보관리업 연계 방식, 가족 열람 구조 |
| 금융소비자보호법 | 상품 "유형" 정보 제공과 판매 권유·중개·자문의 경계. 기획안은 "상품은 유형 예시, 특정 금융회사 상품 아님", "최종 선택과 가입은 본인 결정"(15쪽)으로 설계 |

### B-6. 검증 가능한 AI
- 숫자는 계산엔진이 내고, LLM 답변의 숫자·근거는 엔진 결과와 대조한 뒤에만 화면에 나간다(`07_검증구조.md`). 기획안 23쪽 "계산과 AI를 분리한 검증 가능한 솔루션"이 금융회사(B2B)의 AI 도입 과제(데이터·책임·통제·규정준수)에 대한 답이 된다.
