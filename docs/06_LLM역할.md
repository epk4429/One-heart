## 0. 모든 역할에 공통인 규칙

| 규칙 | 내용 | 근거 |
|---|---|---|
| 출력 형식 | **JSON만** 출력. 역할마다 스키마를 서버에서 검사하고, 틀리면 오류 메시지를 붙여 1회 다시 요청. 그래도 틀리면 해당 화면에 "다시 시도" 표시 | 작은 오픈소스 모델 대비 |
| 숫자 | 금액·기간·비율 숫자를 문장에 **직접 쓰지 않는다.** 엔진 결과의 `fact_id`로 `{{fact:B.goal_hit_years}}`처럼 자리만 표시하고, 화면이 엔진 값을 채운다. 사용자가 말한 숫자를 인용할 때는 `{{quote:…}}` | `07_검증구조.md` |
| 말투 | 존댓말(~요). 금융 용어는 쉬운 말, 어려운 용어는 풀이 | ✅ 4절 7번 |
| 태도 | 누가 옳은지 판단하지 않는다. 결정하지 않고 제안한다 | ✅ 4절 6번, 기획안 13쪽 |
| 입력 경계 | 역할마다 정해진 데이터만 받는다(아래 "볼 수 있는 데이터"). 입력 조립은 서버 코드가 한다 | `03` A-2 |
| 이름 | ⚠️ PoC는 구성원 이름을 그대로 쓴다(가상 인물). 실제 서비스는 가명 치환(`03` B-3) | |
| 설정 | 역할별 최대 토큰 상한. HF는 temperature 0.1. Claude Opus 5.5는 temperature를 받지 않고(보내면 400) 생각이 항상 켜져 있어 `effort`로만 조절한다(기본 medium, 최대 토큰 하한 16,000) | 재현성은 엔진 시드·출력 검사로 지킨다 |

공급자는 `09_시스템구성.md`의 어댑터로 바꾼다(개발: Hugging Face 오픈소스, 통합 테스트부터: Anthropic). 2026-10-06부터 Anthropic `claude-opus-5-5`로 진행한다.

## 역할 1. 이야기·대화 요약

| 항목 | 내용 |
|---|---|
| 화면 | 2 우리 가족 이야기(가족 이야기 구조화), 3 각자의 생각(개인 요약) |
| 볼 수 있는 데이터 | 1-a: 방장이 쓴 이야기만 / 1-b: **해당 구성원의 대화 원문**, 재질문 결과 |
| 출력 1-a | `{"family_stage", "living", "shared_goal", "differences": string[]}` |
| 출력 1-b | `{"keep", "flexible", "worry", "evidence": [{"field", "message_index"}]}` — evidence는 원문 몇 번째 메시지에서 나왔는지(본인 확인 화면에서만 쓰고 가족에게는 안 감) |
| 규칙 | 애매한 말이 해결되지 않았으면 `keep`에 원래 표현을 그대로 두고 `"pending_clarification": true` |
| 골든 | `04` 1-1, 1-3, 2-3 |

## 역할 2. 말뜻 재질문

| 항목 | 내용 |
|---|---|
| 화면 | 3 각자의 생각(1:1 채팅방) |
| 볼 수 있는 데이터 | 해당 구성원의 대화 원문, 구성원 정보(간편 모드 여부) |
| 호출 시점 | 고정 질문 3개에 대한 답이 다 모인 뒤 1회. 재질문 답이 오면 해석 1회 |
| 출력(탐지) | `{"ambiguous": [{"word", "why", "candidates": string[]}], "question", "easy_question", "choices": string[]}` — 간편 모드면 choices 3개 이하, 마지막은 "지금은 잘 모르겠다(나중에 답하기)" |
| 출력(해석) | `{"resolved": bool, "meaning", "confirm_message"}` |
| 규칙 | 다른 가족 앞에서 묻지 않는다(✅ 4절 2번). 끝내 확인되지 않으면 `resolved: false` → 공동 목표 설정이 잠긴다(✅ 4절 3번) |
| 골든 | `04` 2-3 "집을 지킨다" |

## 역할 3. 쟁점 분석

| 항목 | 내용 |
|---|---|
| 화면 | 4 공동 목표 설정 |
| 볼 수 있는 데이터 | 확인된 요약 전원, 가족 이야기 구조화(1-a), 공개를 고른 금융 요약 |
| 출력 | `{"headline", "agreed_points": string[], "issues": [{"title", "left_label", "right_label", "positions": {member_id: 0~1}, "note"}]}` |
| 규칙 | 쟁점 2~4개. `positions`는 요약 근거로 추정하고, 화면은 세 칸으로만 보여 준다. `note`는 기획안 13쪽처럼 한 줄("차이 1~2년", "서연에게 더 중요") |
| 골든 | `04` 1-4, 2-4 (위치는 칸이 같으면 통과) |

## 역할 4. 공동 목표 제안

| 항목 | 내용 |
|---|---|
| 화면 | 4 공동 목표 설정(1단계 제안, 2단계 기준 문장) |
| 볼 수 있는 데이터 | 역할 3 출력, 확인된 요약, 재질문 결과(해결된 뜻) |
| 출력(1단계) | `{"proposal", "to": member_id[], "bridges": [{"issue_title", "how"}]}` — 차이를 좁히는 방법이 쟁점마다 무엇인지 |
| 출력(2단계) | `{"criterion"}` — 답을 반영한 기준 문장. 다음 단계(역할 5)의 목표 조건이 된다 |
| 규칙 | 날짜·금액을 새로 지어내지 않는다. 목표 금액처럼 숫자가 필요하면 가족이 말한 값이나 금융정보 값만 `{{quote}}`로 쓴다 |
| 골든 | 신혼부부 "날짜 대신 조건으로", 노인 가족 "이 집에 사시는 것부터 지키기" |
| 미정 | 다른 의견이 나왔을 때 재제안 → 10절 D1 |

## 역할 5. 선택지 설계 (tool 사용)

| 항목 | 내용 |
|---|---|
| 화면 | 5 미래 계산, 6 합의안(모든 방법에 반대가 있을 때 수정안) |
| 볼 수 있는 데이터 | 공동 목표 기준 문장, 확인된 요약(양보할 수 있는 것 포함), 금융정보(공개 범위 반영 + 서버 합계), 가정값 표(`04` 3절), **후보 조건 범위**(`01` 4절) |
| 도구 | `run_simulation`(`05` 8절). 최대 3회 호출 |
| 출력 | `{"options": Option[3], "design_notes": [{"option_id", "intent"}]}` — Option은 `05` 2절 스키마 |
| 수정안 모드 | 입력에 의사 표시(반대 이유·조건)가 추가된다. 출력 `{"revision": {"from_option_id", "label", "changes": [{"field", "before", "after", "reason_member_id"}], "option": Option}}` |
| 규칙 | 방법 3개는 서로 성격이 달라야 한다(예: 목표 우선 / 균형 / 현재 여유). 양보할 수 있다고 한 것만 조정한다. 엔진이 입력 검사로 거부하면 오류를 보고 고친다 |
| 재현 | `04`의 골든 조건과의 비교는 **개발 테스트에서만** 한다(화면 표시 안 함, `01` 4절). 시연에서 기획안 숫자가 나오도록 입력(월 저축 내역·수익률 가정표·이벤트)을 데이터로 준다 |
| 골든 | `04` 1-5, 2-5, B 조정안 |

## 역할 6. 결과 해석

| 항목 | 내용 |
|---|---|
| 화면 | 5 미래 계산("쉽게 말하면", 사람별 영향), 6 합의안(꼭 지키고 싶은 것 점검표) |
| 볼 수 있는 데이터 | 엔진 결과의 `facts`·`basis`(monthly 표 제외), Option, 확인된 요약 |
| 출력(해석) | `{"easy": "{{fact:…}}가 들어간 한 문장", "per_member": {member_id: "문장"}}` |
| 출력(점검표) | `{"keep_check": {option_id: {member_id: {"ok": bool, "reason"}}}, "note"}` |
| 규칙 | 숫자는 전부 fact 자리표시. 점검표 `reason`도 fact를 쓴다("{{fact:C.goal_hit_years}}, 5년을 넘겨요"). 결론(어느 방법이 좋다)을 말하지 않는다 |
| 골든 | v3 화면 문구, `CONSENT.*.check` |

## 역할 7. 합의안·합의 리포트 작성 (새 역할, 기획안 14쪽)

| 항목 | 내용 |
|---|---|
| 화면 | 6 합의안 |
| 볼 수 있는 데이터 | 확정된 방법(Option + 엔진 결과 facts), 공동 목표 기준, 의사 표시의 조건 목록, 점검표, 수정안 기록 |
| 출력 | `02`의 Agreement 필드 중 글 부분: `goal`, `method.display_label`, `target_amount.label`, `contribution[]`(금액은 Option의 cashflow 참조 id), `timing`, `change_conditions[]`, `commitments[]`(각각 `source`), 그리고 AgreementReport `reasons[]`, `outcomes[]`(fact 참조), `action_plan[]` |
| 규칙 | 조건 하나하나가 약속 하나 이상으로 반영돼야 한다(서버가 검사). 약속마다 출처를 단다. 법적 합의문 표현을 쓰지 않는다("의사결정 기록") |
| 골든 | `04` 1-6, 2-6 |

## 9. 구현 3단계(Python 검증)에서 확인할 것

1. 역할마다 골든 입력으로 5회 호출 → JSON 스키마 통과율, 골든 값 일치율(역할 3은 칸 일치, 역할 5는 옵션 성격과 엔진 결과)
2. 역할 5의 tool 호출이 후보 오픈소스 모델에서 동작하는지. 안 되면 대안: LLM은 Option JSON만 내고 서버가 엔진을 호출한 뒤 결과를 붙여 역할 6으로 넘김(tool 없이)
3. 숫자 자리표시 규칙을 지키는지(검증 구조의 위반 건수)
