# 12. 금융 지식 계층: 상품 온톨로지 + 제도·법 RAG

> 2026-11-02 다시 씀(2026-10-31판을 대체). `08_온톨로지.md`의 가상 상품 유형 14개는 초기 구현용이고, 실제 구현은 이 문서를 따른다.

## 0. 결정

✅ 형님 결정(2026-11-02):
1. **온톨로지의 주축은 실제 금융상품이다.** 여러 금융회사의 실제 상품과 그 요소(금리·기간·위험도·유동성·세제혜택·가입조건·납입 등)로 온톨로지를 만든다. 지금의 가상 상품 유형은 빠른 초기 구현용이었다. 기획안 15쪽의 "상품은 유형 예시이며 특정 금융회사 상품이 아님"은 이 방향으로 바뀐다(기획안 수정은 형님).
2. **실제 상품 데이터는 개발용으로만 구축한다.** 웹에 공개된 실제 상품 몇 가지를 가져와 쓰며, 실제 서비스 데이터로 쓰지 않는다.
3. **화면은 추천이 아니라 "조건 비교·정보 제공"이다.** 선택과 가입은 본인이 한다.
   - (2026-11-03) 다만 금리 순 비교가 아니라 **목표 적합도로 줄 세우고 근거를 보여 준다.**
   - 화면 문구는 **"우리 목표에 잘 맞는 순서예요"**다.
4. **온톨로지는 상품을 토대로 만든 뒤 서비스 전체에서 쓴다.** 단, **실제 상품 언급은 조건 비교 단계에서만** 한다. 공동 목표 제안 등 앞 단계는 재무 원리, 제도, 상품 범주 통계까지만 쓴다(5절).
5. **제도·법은 RAG로 둔다.**
   - 온톨로지(정형)와 RAG(비정형)는 **별개 부품**이다.
   - 둘은 같은 원문 저장소에서 나오고, 서로 ID로 가리킨다.
   - 판단과 계산은 온톨로지가, 설명과 근거는 RAG가 맡는다.
6. **검토자가 없으므로** 사람 검토 대신 기계가 검사할 수 있는 장치로 정확성을 담보한다(9절). (2026-10-31)

⚠️ 이 문서의 구조·파일 배치·검사 기준·단계 계획은 Claude 제안이다(임의결정 51~54).

## 1. 원칙

1. **판단은 코드, 설명은 근거 원문, 선택은 가족.**
   - 자격·적용 금리 판단은 온톨로지 규칙(코드)이 한다.
   - LLM과 RAG 결과로 자격이나 금리를 판단하지 않는다.
2. **금융 제도·상품·숫자는 LLM이 기억으로 말하지 않는다.** 그 역할에 주어진 조회 결과·카드·원문 조각에 있는 것만 쓴다. "숫자는 엔진이 낸다"를 지식에도 똑같이 적용한다.
3. **규칙은 가족 사례가 아니라 상품·제도에 붙인다.** 가족 조합은 끝이 없지만 상품·제도의 조건은 문서에 적혀 있다. 어떤 가족이 와도 조건마다 대조한다.
4. **애매하면 짐작하지 않는다.** 자격 판정은 세 가지다.
   - 충족
   - 불충족
   - 확인 필요
5. **공식 출처만 쓴다.** 모든 노드와 조각에 출처, 원문 구절, 기준일을 붙인다.
6. **파인튜닝하지 않는다.** 상품·제도는 자주 바뀌고, 학습된 지식은 어디서 틀렸는지 추적할 수 없다.

## 2. 전체 구조

```
지식 계층
 ├─ 원문 저장소 (공시 API 응답·상품설명서·법령·제도 안내, 기준일·해시)      ← 3절. 아래 둘이 모두 여기서 나온다
 │
 ├─ 상품 온톨로지 (정형)                                                ← 4절
 │    실제 상품 ─ 옵션(기간·금리) ─ 자격·우대 조건(규칙) ─ 금융회사
 │       └─ 범주(적금·정기예금·연금저축·전세대출…) ─ 범주 통계
 │    제도(공적·정책금융) ─ 자격 규칙
 │    재무 원리 카드
 │         → 판단·계산: 자격 판정, A에게 적용되는 금리, 범주 통계, 레버
 │
 └─ 제도·법 RAG (비정형)                                                ← 7절
      원문 조각(법령 조문·제도 안내·FAQ) + 검색 색인 + 온톨로지 노드 태그
           → 설명·근거: "근거 보기", 제도 설명, 예외 안내 (판단에는 안 씀)

연결: 온톨로지 노드 ─source_id→ 원문 / RAG 조각 ─node_tags→ 온톨로지 노드
```

## 4. 상품 온톨로지

### 4.1 데이터 출처: 금감원 오픈 API (2026-11-02 공식 페이지 확인)

8종을 제공한다: 금융회사개요, 정기예금, 적금, 연금저축, 주택담보대출, 전세자금대출, 개인신용대출, 개인사업자대출.
- **(2026-11-03 전 범주 수집 결과)** 서비스 이름: `depositProductsSearch`, `savingProductsSearch`, `mortgageLoanProductsSearch`, `rentHouseLoanProductsSearch`, `creditLoanProductsSearch`, `busiLoanProductsSearch`, `companySearch`(각 안내 페이지 테스트 양식에서 확인).
- **연금저축(`annuitySavingProductsSearch`)은 응답이 비정상**이라 뺐다. 보험 권역은 46건이라면서 4건만 오고 그마저 대출 상품이며, 금융투자 권역은 297건이라면서 모든 쪽이 빈 목록이다. 다른 공식 출처(예: 금감원 통합연금포털)를 찾아야 한다.
- **저축은행은 정기예금·적금에 같은 상품 코드를 다른 상품에 쓴다**(예: 하나저축은행 240010). 그래서 상품 ID에 범주를 넣는다: `PRD_<범주>_<회사>_<상품>`. 연금저축은 안내 페이지의 요청 주소가 적금과 같게 적혀 있어(오기로 보임) 서비스 이름을 아직 확인하지 못했다. 짐작한 이름으로 부르면 연금 항목이 빈 응답이 온다.
- 권역은 은행, 여신전문, 저축은행, 보험, 금융투자이고, XML·JSON으로 받는다.
- 1회 최대 100건이며, 개인 인증키는 일일 호출 횟수 제한이 있다(응답코드 020).
- 인증키는 형님이 신청해 `.env`의 `FINLIFE_API_KEY`에 넣는다. 저장소와 대화에는 넣지 않는다.

| API | 기본정보(baseinfo) | 옵션(options) |
|---|---|---|
| 적금 (정기예금도 거의 같음) | 금융회사·상품명·상품코드, 가입 방법, 만기 후 이자율, **우대조건(글)**, 가입제한(1 제한없음·2 서민전용·3 일부제한), **가입대상(글)**, 기타 유의사항, 최고한도, 공시 기간 | 금리 유형, 적립 유형(정액·자유), 저축 기간(개월), 저축 금리, 최고 우대금리 |
| 연금저축 | 연금종류, 상품유형, 공시이율, 최저 보증이율, 과거 3년 수익률, 판매사, 판매 개시일 | (적금과 같은 금리 옵션) |
| 전세자금대출 (주택담보대출 비슷) | 대출 부대비용, 중도상환 수수료, 연체 이자율, 대출한도 | 상환유형, 금리유형, 대출금리 최저·최고, 전월 취급 평균금리 |

**API로 바로 안 되는 것 = 온톨로지가 할 일**
- **가입대상·우대조건이 글이다.** 예: "급여이체 시 0.3%p". 이것을 **조건 규칙**(4.3)으로 구조화해야 자격 판정과 적용 금리 계산이 된다. 구조화는 8절의 추출 절차로 한다.
- **API에 없는 속성:** 세제혜택, 위험도, 중도해지 조건(유동성), 납입 상세. 이것은 상품설명서 스냅샷에서 추출하거나 범주 기본값으로 둔다.
  - 범주 기본값의 예: 예금·적금 = 원금보장(예금자보호 대상인지는 원문 확인).
- **API 밖 범주:** 보험(태아·간병), 주택연금·정책대출 같은 공적 제도, 모임통장. 공식 안내문으로 Program 또는 Product를 만든다.

### 4.2 클래스와 관계

```
Provider(금융회사) ─offers→ Product(실제 상품) ─inCategory→ Category(적금·정기예금·연금저축·전세대출·…·보험·모임통장)
Product ─hasOption→ Option(기간·적립유형·금리유형·기본금리·최고우대금리)
Product ─eligibleIf→ Condition(가입 자격 규칙)
Product ─bonusIf→ Benefit(우대금리 +x%p ← Condition)
Product ─hasAttribute→ Attribute(위험도·유동성·세제·납입·한도·중도상환수수료…)
Category ─summarizedBy→ CategoryStats(기간별 금리 분포, 표본 수, 기준월)
Program(제도·정책금융) ─eligibleIf→ Condition / ─enables→ Lever(방법 설계에 쓸 수 있는 방법)
Need(합의안 약속의 필요) ─servedBy→ Category / Program        ← 지금 vocab.json의 Need를 이어 씀
Constraint(약속의 제약) ─filters→ Attribute 조건                 ← 지금 rules.json을 이어 씀
모든 노드 ─source→ Source(원문 구절)
```

### 4.4 변수와 세 가지 판정

- **변수는 정해진 목록(`variables.json`)에서만 쓴다.** 변수마다 가족 입력에서 값을 얻는 방법이 정해져 있다.
  - 예: `age`, `home_count`, `household_annual_income`, `has_child_under_2`, `salary_transfer`
- **가족 입력으로 알 수 없는 값은 `unknown`이다.** 예: 신용점수, 주거래 실적, 건강 상태.
  - 이 변수가 걸린 조건은 자동으로 **확인 필요**가 된다.
  - 추정값도 확인 필요로 처리한다. 예: 월 수입 × 12를 연소득으로 쓰는 경우.

| 판정 | 기준 | 화면 |
|---|---|---|
| 충족 | 모든 자격 조건을 변수로 확인함 | 비교 표에 포함 |
| 불충족 | 조건 하나라도 확실히 안 맞음 | 빼고, "왜 빠졌나요"에 사유 표시 |
| 확인 필요 | unknown 변수·단서 조항·검사 미통과가 걸림 | 포함하되 "○○ 조건은 금융회사에서 확인하세요" + 원문 |

**A에게 적용되는 금리** = 기본금리 + (충족한 우대조건의 더하기 합, 최고 우대금리 이하)이다. 확인 필요 우대조건은 "최대 ○%까지 가능"으로 따로 보여 준다.

**우대 항목의 종류**(`conditions.json`의 `tags`)
- **action:** 본인이 하면 받는 것. 급여이체, 카드, 자동이체, 마케팅 동의, 비대면 가입, 상품 함께 가입, 목표·미션, 쿠폰·특판.
  - 조건 비교 화면에서 "이렇게 하면 받아요"로 고르게 한다.
- **attribute:** 사람의 조건. 나이, 출산·자녀, 무주택, 복지 대상, 직업.
  - 가족 정보로 판정하거나, 판정할 수 없으면 확인 필요로 둔다.
- **relation:** 그 금융회사와의 거래 관계. 첫 거래, 주거래, 등급.
  - 가족 정보로 알 수 없어 확인 필요로 둔다.

### 4.5 범주 통계

- 실제 상품들을 범주·기간별로 묶어 금리 분포(최저·중간·최고, 표본 수, 기준월)를 만든다(`category_stats.json`).
- 이것이 앞 단계에 올라가는 상품 지식이다. **상품 이름은 나가지 않는다.**
- 쓰는 곳 1, 방법 설계의 수익률 가정값: 지금 `data/assumptions.json`의 가상값을 "적금 12개월 중간 금리 연 ○%(○월 공시 ○개 상품)"으로 바꾼다.
- 쓰는 곳 2, 결과 해석의 근거 문장.

## 5. 단계별로 쓰는 지식 (접근 범위)

| 지식 | 각자의 생각·공동 목표 제안 (역할 1·3·4) | 방법 설계·결과 해석 (역할 5·6) | 합의안 (역할 7) | 조건 비교 (화면 7, 역할 8) |
|---|---|---|---|---|
| 재무 원리 카드 | ✅ | ✅ | ✅ | ✅ |
| 제도 | △ 종류만("출산 가구 지원 제도가 있어요") | ✅ 레버·조건으로 | ✅ | ✅ |
| 상품 범주 통계 | ✗ | ✅ 가정값·근거로(상품 이름 없이) | ✗ | ✅ |
| 실제 상품 | ✗ | ✗ | ✗ | ✅ 여기서만 |
| 제도·법 RAG | ✗ | △ 레버 설명 근거 | ✗ | ✅ "근거 보기" |

- **막는 방법은 구조다.** 역할마다 받을 수 있는 조회 도구·카드를 서버가 정한다.
  - 예: 공동 목표 역할에는 상품 조회 도구 자체가 없다.
  - 출력에 상품명·회사명이 나오면 검사에서 실패로 처리한다(금융회사명 목록과 대조).
- **역할 4(공동 목표 제안):** 재무 원리 카드와 이 가족 상황에 해당하는 제도 종류만 받는다. "날짜 대신 조건으로" 같은 제안은 원리(비상금, 휴직 중 소득 감소)에 근거하고, 상품으로 답을 정해 주지 않는다(4절 6번: AI는 결정을 대신하지 않는다).
- **조건 비교 화면(지금의 '상품 추천' 화면 아래, 2026-11-03 구현, `ontology/fit.py`·`/api/products/fit`, AI 없음):**
  - **대상:** 합의안 약속이 '적금' 유형으로 이어진 필요마다 실제 상품 목록을 붙인다.
  - **입력:** 누구 이름으로(나이), 매달 넣을 돈, 기간, "내가 할 수 있는 우대 조건"(급여 옮기기·자동이체·마케팅 동의 등). 화면에서 고친다.
  - **줄 세우는 순서:**
    1. 가입 나이가 안 맞으면 빼고 사유를 보여 준다.
    2. 매달 넣을 돈이 월 한도 안인가.
    3. 만기 세후 이자(원, 1만원 단위로 묶음).
    4. 확인 필요 조건이 있는가.
    5. 할 일 수.
  - 금리 %만으로 줄 세우지 않는다. 0.05%p 차이는 월 60만원 1년에 2천원 남짓이다.
  - **보여 주는 것:**
    - 상품마다: 내가 받을 금리, 만기 금액, 받는 우대(초록), 하면 더 받는 우대(회색), 해당되면 받는 우대·확인 필요(노랑)
    - 1번 상품: 근거 문장(약속 → 한도 → 금리 → 만기 금액)
    - 나머지 상품: "1번보다 아래인 이유"
    - 근거 보기: 우대조건 원문, 가입대상, 한도 원문, 공시 기준월
  - 기본 5개를 보여 주고 "더 보기"로 나머지를 연다.
  - 문구는 "우리 목표에 잘 맞는 순서예요. 추천이 아니라 정보예요. 선택과 가입은 직접 해요"로 한다.
  - 공개 배포(Vercel)에서는 끈다(`REAL_PRODUCTS`, 공시 데이터 공개 사용 조건 확인 전).

## 6. 재무 원리 카드

- **무엇인가:** 상품·제도가 아닌 일반 원리다. 예: 비상금은 몇 달치 생활비, 빚 갚기와 저축의 비교, 기간이 짧은 돈은 원금보장, 휴직 중 소득 변화.
- **규모와 형식:** 20~40개로 작고, 카드 한 장은 2~3문장에 출처를 붙인다(`knowledge/cards.json`).
- **넣는 방식:** 수가 적어서 검색하지 않는다. 역할마다 태그로 정해 둔 카드 묶음을 넣는다.
- **원리가 숫자로 쓰일 때:** 예를 들어 "비상금 6개월"이 계산에 들어가면 가족 입력으로 만든 fact와 같은 방식으로 검증한다.

## 7. 제도·법 RAG

| 항목 | 내용 |
|---|---|
| 문서 | 법령 조문(법제처 API), 제도 안내문·FAQ(3절 출처), 상품 약관 중 설명 부분 |
| 조각 | 법령은 조문 단위, 안내문은 제목 단위(300~800자). 조각마다 `chunk_id`, `source_id`, 기준일, **온톨로지 노드 태그**(예: `PP_reverse_mortgage`) |
| 검색 | 처음엔 키워드 검색(BM25, 한글은 글자 n-gram)으로 시작한다. 문서가 수백 조각 수준이라 충분하다. 벡터 검색이 필요해지면 임베딩 공급자를 바꿀 수 있게 둔다(Anthropic은 임베딩 API가 없다) |
| 검색 범위 | 온톨로지로 먼저 해당 제도·상품을 고른 뒤, 그 노드에 태그된 조각 안에서만 검색한다(엉뚱한 문서 방지) |
| 쓰는 곳 | 조건 비교의 "근거 보기", 제도 설명, 예외·단서 안내, 방법 설계 레버의 설명 근거 |
| 안 쓰는 곳 | 자격 판정, 금리·한도 숫자. 이것은 온톨로지 규칙만 쓴다 |
| 검사 | LLM이 RAG로 답할 때 `chunk_id` + 인용 구절을 달게 하고, 서버가 그 구절이 그 조각에 글자 그대로 있는지 확인한다(9절 G3·G11) |

## 8. 구축 절차

```
① 수집 → ② 스냅샷 → ③ 적재(API) / 추출(문서) → ④ 2차 독립 추출 → ⑤ 자동 검사 → ⑥ 원문 사례 테스트 → ⑦ 반영
```

1. **수집**
   - 공시 API: `tools/fetch_finlife.py`가 범주별로 전체 페이지를 받는다.
   - 문서: 허용 목록 출처만 받는다.
2. **스냅샷:** 원본을 `knowledge/sources/`에 수집일·sha256과 함께 저장한다.
3. **적재·추출**
   - API의 정형 항목(금리·기간·한도 등)은 코드가 그대로 노드로 옮긴다. 추출이 필요 없다.
   - 글 항목(우대조건·가입대상)과 문서는 Claude Code 세션에서 Condition·Benefit·Card 초안으로 바꾼다. 모든 항목에 원문 구절을 붙인다. 체험판 Anthropic 예산은 쓰지 않는다.
4. **2차 독립 추출:** 앞 결과를 보지 않은 별도 에이전트가 같은 원문에서 다시 추출한다.
   - **(2026-11-02 공시 상품에 실제 적용한 방식)** 우대조건은 코드(`ontology/conditions.py`)가 줄 단위로 나눠 금액·종류·묶음을 뽑는다.
   - 독립 대조는 두 갈래다.
     - **공시의 정형 숫자 대조:** "최고 우대금리 − 기본금리"는 금융회사가 글과 따로 제출한 값이라, 뽑은 우대 합계(상한·택일·단계형 반영)와 비교한다.
     - **사람이 원문을 읽고 적은 정답 사례:** `tests/test_conditions.py`에 고정한다.
   - 상태는 세 가지다.
     - `verified`: 합계가 공시와 맞음
     - `capped`: 항목은 다 뽑혔고 합계가 공시보다 큼(택일·기간별 차등) → 공시 최고 우대를 상한으로 씀
     - `needs_check`: 공시보다 적게 뽑힘, 금액이 원문에 없음, 읽지 못한 항목
   - 우대금리와 가입자격 상태를 따로 둔다.
5. **자동 검사:** `tools/kb_check.py`가 9절 검사를 돌린다. 하나라도 실패하면 `needs_check`로 둔다.
6. **원문 사례 테스트:** 상품설명서·FAQ의 예시를 테스트로 만든다(`tests/test_knowledge.py`). 원문에 사례가 없으면 경계값 사례를 만들고 "원문 사례 아님"을 표시한다.
7. **반영:** `verified`만 충족·불충족 판정에 쓴다. 나머지는 확인 필요로만 쓴다.

## 9. 정확성 장치 (검토자 없음)

| | 장치 | 막는 것 | 확인 방법 |
|---|---|---|---|
| G1 | 출처 허용 목록 | 비공식·광고 출처 | 수집 도구가 도메인 검사 |
| G2 | 원문 스냅샷 + 해시 | 근거가 나중에 사라짐 | 저장소 보관, 해시 비교 |
| G3 | 인용 글자 일치 | 출처·구절 지어내기 | `quote`가 스냅샷에 그대로 있는지(공백 정리 후) 코드로 검사 |
| G4 | 숫자 일치 | 숫자 잘못 옮기기 | 규칙·카드의 모든 숫자가 인용 구절 안에 있는지 검사 |
| G5 | 두 번 독립 추출 | 해석 실수 | 두 추출의 변수·연산자·값이 다르면 `needs_check` |
| G6 | 단서 조항 감지 | 예외 누락 | 인용 주변에 "다만·제외·경우에 한하여·단," 등이 있으면 `caveats`가 비어 있을 수 없음 |
| G7 | 원문 사례 테스트 | 규칙 코드화 실수 | 원문 예시로 판정 결과 비교 |
| G8 | 보수적 기본값 | 애매한 걸 단정 | unknown·단서·검사 실패는 모두 확인 필요 |
| G9 | 기준일·만료 | 개정·공시 변경 미반영 | 상품은 공시월 기준 3개월, 제도·법은 수집 후 6개월이 지나면 `expired` |
| G10 | 화면 표시 | 단정·추천으로 받아들임 | 출처·기준일·"개발용 예시 데이터"·"최종 확인은 금융회사·기관에서" |
| G11 | 실행 중 인용 검사 | LLM이 주어지지 않은 상품·제도·조각을 말함 | 출력의 노드 ID·`chunk_id`가 그 호출에 준 것인지, 인용이 조각에 있는지 서버가 검사 |
| G12 | 단계별 노출 검사 | 앞 단계에서 상품 언급 | 역할 4·5·6·7 출력에 금융회사명·상품명이 있으면 실패 |

- **보증하는 것:** 모든 규칙·카드·숫자가 공식 원문에 글자 그대로 근거를 두고, 숫자가 원문과 같다.
- **보증하지 못하는 것:** 원문 해석의 정확성(예외 조항 적용, 용어 정의), 원문 자체의 모호함, 스냅샷 이후의 변경.
- **대응:** 해석이 끼는 조건은 G5·G6·G8로 확인 필요에 떨어뜨린다. 심사 때도 이 한계를 설계로 설명한다.

## 10. 지식 밖의 상황

- **계속 동작하는 것:** 엔진 계산과 합의 흐름은 그대로 돈다. 숫자는 가족이 넣은 값으로 계산한다.
- **해당 상품·제도가 없을 때:** "이 상황은 아직 다루는 상품·제도가 없어요. 금융회사·전문가 상담을 권해요"라고 표시한다. LLM이 기억으로 상품·제도를 말하지 못하게 막는다(1절 2, G11).
- **빈칸 기록:** 지식 밖 상황과 확인 필요 판정을 집계해 다음에 채울 범주·제도의 근거로 쓴다. 배포본에서는 가족 데이터 없이 태그 이름만 센다.
