# 12. 금융 도메인 지식 구축 (온톨로지 고도화)

> 2026-10-31 작성. `08_온톨로지.md`(상품 추천 층)를 서비스 전체의 뼈대로 넓히는 설계다.
> ✅ 형님 결정(2026-10-31): ① 온톨로지는 상품 추천만이 아니라 **서비스 전체가 기대는 뼈대**로 만든다. ② **검토자가 없으므로** 사람 검토 대신 기계가 검사할 수 있는 장치로 정확성을 담보한다.
> ⚠️ 이 문서의 구조·파일 배치·범위·숫자 기준은 Claude 제안이다(임의결정 43~47).

## 1. 원칙

1. **금융 제도와 숫자는 LLM이 기억으로 말하지 않는다.** 지식베이스에 있고 그 역할에 주어진 카드만 쓴다. 숫자를 엔진이 내는 지금 구조를 지식에도 똑같이 적용한다.
2. **판단은 코드, 설명은 카드, 선택은 가족.**
   - 자격·한도·세제 판단은 규칙(코드)이 한다.
   - 설명은 출처가 붙은 짧은 카드로 한다.
   - 가치 판단(집 먼저 vs 아이 먼저)은 규칙으로 정하지 않는다.
3. **규칙은 가족 사례가 아니라 제도에 붙인다.** 가족 조합은 끝이 없지만 다룰 제도는 셀 수 있다. 어떤 가족이 와도 제도마다 조건을 대조한다.
4. **애매하면 짐작하지 않는다.** 자격 판단은 세 가지로 낸다.
   - 충족
   - 불충족
   - 확인 필요
5. **공식 출처만 쓴다.** 모든 지식에 출처, 원문 구절, 기준일을 붙인다. 블로그·금융사 광고·LLM 기억은 출처가 아니다.
6. **파인튜닝하지 않는다.** 제도는 매년 바뀌고, 학습된 지식은 어디서 틀렸는지 추적할 수 없다.

## 2. 지금 상태와 문제

지식이 네 곳에 흩어져 있고, 온톨로지는 마지막 화면(상품 추천)에만 쓰인다.

| 지식 | 지금 위치 | 문제 |
|---|---|---|
| 필요·제약·상품 유형 | `ontology/vocab.json`, `rules.json`, `product_types.json`(필요 14·제약 7·유형 14·규칙 7) | 화면 7에서만 씀. 가입조건·세제는 "확인 필요" |
| 자격 조건 | `vocab.json`의 `requires`(집·나이·상환 대출) | 손으로 넣은 몇 개뿐. 72세에게 연금저축 추천됨 |
| 쓸 수 있는 방법(정책 블록) | `llm/plan.py policy_menu` | 코드에 하드코딩. 정책대출·청약 등 없음 |
| 기준값 | `data/assumptions.json` | 물가 2% 말고는 가상값. 주택연금 비율도 가상(임의결정 25) |
| 상황 해석·갈등 유형 | `llm/roles.py` 프롬프트 | 어휘가 없어 매번 AI가 즉석으로 판단 |

## 3. 전체 구조

```
                ┌───────────── 출처(Source): 공식 원문 스냅샷 · 기준일 · 해시 ─────────────┐
                │                         ↑ cites (모든 노드)                              │
가족 입력 ──→ 상황(Situation) ──→ 목표 유형(GoalType) ──→ 필요(Need) ──→ 제약(Constraint) ──→ 상품 유형(ProductType)
   │            │                                         │                                   ↑
   │            ├──→ 갈등 유형(ConflictType)              └──→ 방법(Lever) ──→ 엔진 입력         │
   │            └──→ 제도(Program) ── 자격 규칙(Rule) ─────────────┴───────────────────────────┘
   └─ 코드가 직접 판정(나이·집·대출·자녀)  /  LLM이 어휘에서 골라 판정(이야기 속 사건, 근거 인용 필수)
```

| 층 | 뜻 | 예 | 누가 정하나 | 쓰는 역할 |
|---|---|---|---|---|
| Situation | 가족이 처한 사실 | 무주택, 전세 거주, 출산 예정, 은퇴, 간병 중, 원리금 상환 중 | 코드(입력에서) + LLM(이야기에서, 인용 필수) | 전부 |
| GoalType | 목표의 종류 | 목표 금액 모으기 / 예금이 버티는 기간 / 대출 다 갚기 | 지금 엔진의 3종 그대로 | 4b, 5 |
| ConflictType | 갈등의 성격 | 순서, 가치, 위험 성향, 분담 | LLM(어휘에서) | 3, 4a |
| Need | 채워야 할 필요 | 휴직 준비금, 생활비 재원, 비상금 | LLM 역할 8(어휘에서) | 7, 8 |
| Lever | 계산에 넣을 수 있는 방법 | 더 갚기, 한 번에 갚기, 주택연금, 집 줄이기, 정책대출 갈아타기 | 코드(적용 조건 판정) + LLM(고르기) | 5, 5r |
| Constraint | 약속이 거는 조건 | 원금 보장, 바로 꺼냄, 집에 계속 살기 | LLM 역할 8(어휘에서) | 8 |
| Program | 정책금융·공적 제도 | 주택연금, 디딤돌대출, 신생아특례대출, 청약, 육아휴직급여 | 지식베이스 | 5, 6a, 8 |
| ProductType | 상품 유형(특정 회사 아님) | 적금, 수시입출금, 모임통장 | 지식베이스 | 8 |
| Rule | 자격·한도·세제 조건 | "나이 ≥ ○세", "주택 수 = 0" | 지식베이스(원문 인용) | 코드 |
| Card | LLM에게 주는 설명 조각 | "주택연금은 집에 살면서 매달 받는 공적 제도예요" | 지식베이스(원문 인용) | 해당 역할 |

**흐름이 바뀌는 곳**
- **역할 5(방법 설계):** `policy_menu` 대신 "이 가족이 쓸 수 있는 Lever 목록"을 받는다. 목록은 Situation과 Program 자격으로 코드가 만든다. Lever마다 근거 카드가 붙는다.
- **역할 3·4a(쟁점·제안):** 갈등 유형 어휘를 받아 고른다. 고른 유형에 따라 제안 방식 안내가 달라진다. 예: 순서 갈등이면 "날짜 대신 조건으로".
- **역할 8·추천:** 지금 구조 그대로 쓰되, 상품·제도마다 자격 규칙을 세 가지 판정으로 돌린다.

## 4. 지식 단위 (스키마)

### 4.1 Source: 원문 스냅샷

```jsonc
{
  "source_id": "S_hf_reverse_mortgage_eligibility",
  "publisher": "한국주택금융공사",
  "url": "(수집 때 기록)",
  "title": "주택연금 가입요건",
  "fetched_at": "2026-11-0X",
  "effective_date": "원문에 적힌 시행일(없으면 null)",
  "sha256": "...",
  "file": "ontology/sources/S_hf_reverse_mortgage_eligibility.txt"   // 본문 텍스트만 저장
}
```

### 4.2 Rule: 자격·한도 조건

```jsonc
{
  "rule_id": "R_reverse_mortgage_age",
  "applies_to": "PP_reverse_mortgage",
  "kind": "eligibility",                 // eligibility | limit | tax | benefit_amount
  "condition": {"var": "oldest_spouse_age", "op": ">=", "value": "○○"},  // 값은 원문에서
  "quote": "원문 구절 그대로",
  "source_id": "S_hf_reverse_mortgage_eligibility",
  "caveats": ["원문의 '다만 ~' 구절"],      // 예외·단서가 있으면 기록
  "status": "verified",                  // draft | verified | needs_check | expired
  "checks": {"quote_match": true, "numbers_in_quote": true, "double_extract": "agree"}
}
```

- **변수(var)는 정해진 목록에서만** 쓴다. 각 변수는 가족 입력에서 계산하는 방법이 정해져 있다(`ontology/variables.json`).
  - 예: `oldest_spouse_age`, `home_count`, `home_price`, `household_annual_income`, `has_child_under_2`
- 가족 입력으로 값을 알 수 없는 변수는 `unknown`이다.
  - 예: 공시가격, 신용점수, 건강 상태
  - 이 변수가 걸린 규칙은 자동으로 **확인 필요**가 된다.
- 추정값도 확인 필요로 처리한다. 예: 월 수입 × 12를 연소득으로 쓰는 경우.

### 4.3 판정: 세 가지 답

```
모든 규칙 충족                      → 충족       : 추천·방법에 포함
규칙 하나라도 확실히 불충족          → 불충족     : 제외, 제외 사유 표시(지금 excluded와 같음)
unknown 변수·caveats·needs_check 포함 → 확인 필요 : 포함하되 "○○ 조건은 기관에서 확인하세요" + 출처
```

### 4.4 Lever: 쓸 수 있는 방법

```jsonc
{
  "lever_id": "L_reverse_mortgage",
  "label": "주택연금(지금 집에 계속 살면서 매달 받기)",
  "requires_program": "PP_reverse_mortgage",   // Program 판정이 불충족이면 메뉴에서 빠짐
  "requires_situation": ["owns_home"],
  "engine_block": "reverse_mortgage",          // plan.py가 아는 블록 이름(엔진 입력 변환은 지금 코드)
  "amount_basis": "R_reverse_mortgage_payment_table",  // 금액 근거 규칙(지급표)
  "card_ids": ["K_reverse_mortgage_what", "K_reverse_mortgage_tradeoff"]
}
```

### 4.5 Card: LLM에게 주는 설명

```jsonc
{
  "card_id": "K_reverse_mortgage_tradeoff",
  "text": "주택연금을 받으면 매달 생활비가 생기지만, 나중에 물려줄 집의 몫은 줄어요.",  // 쉬운 말, 2문장 이하
  "quote": "근거 원문 구절", "source_id": "...", "status": "verified"
}
```

## 5. 범위: 생애 단계 × 필요

금융 전체를 넣지 않는다. 체험 가족이 실제로 마주칠 칸만 채운다.

| 생애 단계 \ 영역 | 주거 | 출산·육아 | 노후·간병 | 부채 | 저축·투자 |
|---|---|---|---|---|---|
| 신혼 | 청약, 신혼부부 정책대출, 전세대출 | 육아휴직급여, 부모급여 | — | 전세대출 이자 | 적금, 비상금 |
| 자녀 양육 | 청약, 정책대출 | 아동수당 | — | 원리금 상환 | 교육비 |
| 한부모 | 공공임대·정책대출 | 한부모 지원 | — | — | 비상금 |
| 은퇴 전 | 갈아타기 | — | 연금저축·IRP | 중도상환 | 노후 자금 |
| 은퇴 후 | 주택연금, 집 줄이기 | — | 기초연금, 장기요양보험, 간병 | — | 병원비 통장 |

- 예상 규모: 제도 30~40개, 규칙 50~80개, 카드 100개 안팎.
- 각 칸의 실제 제도명·조건은 수집 단계에서 원문으로 확정한다. 위 표는 수집 대상 목록일 뿐 사실 주장이 아니다.
- **1차 범위(파일럿): 주거.** 청약, 정책 구입대출, 전세대출, 주택연금, 집 줄이기가 대상이다. 예시 가족 2개와 평가 가족 2개(한부모·대출 부부)에 모두 걸린다.

### 출처 허용 목록 (G1)

| 종류 | 기관(사이트) |
|---|---|
| 법령 | 국가법령정보센터(법제처, 공동활용 API) |
| 주거 | 주택도시기금, 한국주택금융공사, 청약홈(한국부동산원) |
| 복지·고용 | 복지로, 고용노동부·고용24, 국민연금공단, 국민건강보험공단 |
| 시장·통계 | 한국은행 ECOS, 통계청 KOSIS, 공공데이터포털 |
| 금융상품 | 금융감독원 "금융상품 한눈에", 금융위원회 |

정확한 URL은 수집할 때 Source에 기록한다. 목록에 없는 도메인은 수집 도구가 거부한다.

## 6. 구축 절차

```
① 수집 → ② 스냅샷 → ③ 1차 추출 → ④ 2차 독립 추출 → ⑤ 자동 검사 → ⑥ 원문 사례 테스트 → ⑦ 반영
```

1. **수집:** 범위 표의 제도마다 허용 목록 출처에서 가입요건, 지원 내용, FAQ 페이지를 찾는다.
2. **스냅샷:** 본문 텍스트를 `ontology/sources/`에 저장하고 수집일과 sha256을 기록한다. 원문이 바뀌면 해시로 알 수 있다.
3. **1차 추출:** Claude Code 세션에서 원문을 읽고 Rule·Card 초안을 만든다. 모든 항목에 원문 구절을 붙인다. Claude Code 작업이라 체험판 Anthropic 예산은 쓰지 않는다.
4. **2차 독립 추출:** 앞 결과를 보지 않은 별도 에이전트가 같은 원문에서 다시 추출한다.
5. **자동 검사:** `tools/kb_check.py`가 6절 표의 검사를 돌린다. 하나라도 실패하면 `needs_check`로 둔다.
6. **원문 사례 테스트:** 기관 FAQ·안내에 나온 사례를 테스트로 만든다(`tests/test_knowledge.py`). 원문에 사례가 없으면 경계값 사례를 만들되 테스트 이름에 "원문 사례 아님"을 표시한다.
7. **반영:** 상태가 `verified`인 것만 실행 중에 "충족·불충족" 판정에 쓴다. 나머지는 "확인 필요"로만 쓴다.

## 7. 정확성 담보 장치 (검토자 없음)

| | 장치 | 무엇을 막나 | 어떻게 확인 |
|---|---|---|---|
| G1 | 출처 허용 목록 | 비공식·광고 출처 | 수집 도구가 도메인 검사 |
| G2 | 원문 스냅샷 + 해시 | 출처가 나중에 바뀌어 근거가 사라짐 | 저장소에 보관, 해시 비교 |
| G3 | 인용 글자 일치 | 출처·구절을 지어냄 | `quote`가 스냅샷 본문에 그대로 있는지(공백 정리 후) 코드로 검사 |
| G4 | 숫자 일치 | 숫자를 잘못 옮김 | 규칙·카드에 쓴 모든 숫자가 인용 구절 안에 있는지 검사 |
| G5 | 두 번 독립 추출 | 해석 실수 | 두 추출의 조건(변수·연산자·값)이 다르면 `needs_check` |
| G6 | 단서 조항 감지 | 예외를 놓침 | 인용 주변에 "다만·제외·경우에 한하여·단," 등이 있으면 `caveats`가 비어 있을 수 없음 |
| G7 | 원문 사례 테스트 | 규칙 코드화 실수 | 기관 FAQ 사례로 판정 결과 비교 |
| G8 | 보수적 기본값 | 애매한 걸 단정 | unknown 변수·단서·검사 실패는 모두 "확인 필요" |
| G9 | 기준일·만료 | 개정 미반영 | 수집일 + 6개월이 지나면 `expired` → 화면에 "기준일 지남, 확인 필요" |
| G10 | 화면 표시 | 사용자가 단정으로 받아들임 | 출처 기관·기준일·"최종 확인은 해당 기관에서" 표시 |
| G11 | 실행 중 인용 검사 | LLM이 카드에 없는 제도를 말함 | 역할 출력의 `card_ids`가 그 호출에 준 카드인지 서버가 검사(`{{fact:ID}}` 검증과 같은 방식) |

**보증하는 것과 못 하는 것**
- ✅ 보증: 모든 규칙·카드가 공식 원문에 **글자 그대로** 근거를 두고, 숫자가 원문과 같다.
- ❌ 보증 못 함: 원문 **해석**의 정확성(예외 조항 적용, 용어 정의), 원문 자체의 모호함, 스냅샷 이후의 개정.
- 대응: 해석이 끼는 조건은 G5·G6·G8로 "확인 필요"에 떨어뜨린다. 심사 때도 이 한계를 설계로 설명한다.

## 8. LLM에게 넣는 방식

1. **역할마다 필요한 카드만 넣는다.**
   - 역할 5에는 이 가족이 쓸 수 있는 Lever의 카드만 넣는다.
   - 역할 6a에는 결과 해석에 걸리는 제도 카드만 넣는다.
   - 카드 전체를 넣지 않는다. 비용이 늘고 엉뚱한 제도를 꺼낼 수 있기 때문이다.
2. **프롬프트 규칙을 추가한다.** "금융 제도·상품·세금·자격에 대해서는 주어진 카드에 있는 내용만 쓴다. 카드에 없으면 '이 부분은 기관 확인이 필요해요'라고 쓴다."
3. **출력에 카드 ID를 단다.** 제도를 언급한 문장에는 `card_ids`를 붙이고 서버가 검사한다(G11).
4. **화면에 "근거 보기"를 둔다.** 방법·상품 옆에서 카드 → 원문 구절 → 기관·기준일까지 펼친다.
5. **공개 범위 원칙은 그대로다.** 카드는 공개 지식이라 어느 역할에 넣어도 된다. 상황 판정에 쓰는 가족 데이터는 지금처럼 역할별 공개 범위를 따른다.
6. **비용:** 카드는 역할당 수백~수천 토큰이다. 늘어나는 가족당 비용은 평가(11절)에서 측정하고, 목표는 지금 대비 +20% 이내로 둔다.

## 9. 지식베이스 밖의 상황

- **상황 판정:** LLM이 이야기에서 상황을 고를 때 어휘에 없으면 `other`로 두고, 짧은 설명과 원문 인용을 남긴다.
- **계속 동작하는 것:** 엔진 계산과 합의 흐름은 그대로 돈다. 숫자는 가족이 넣은 값으로 계산한다.
- **제도·상품 쪽 처리:** "이 상황은 ONE-Heart가 아직 다루지 않아요. 전문가 상담을 권해요"라고 표시한다. LLM이 기억으로 제도를 말하지 못하게 막는다(8절 2·3).
- **빈칸 기록:** `other` 상황과 "확인 필요" 판정을 집계해 다음에 채울 제도의 근거로 쓴다.
  - 로컬: 사용 장부처럼 파일에 기록한다.
  - 배포본: 가족 데이터는 남기지 않고, 상황 태그 이름만 센다.

## 11. 평가

전후를 같은 가족들로 비교해야 "품질이 올랐다"고 말할 수 있다.

- **평가 가족(8개 목표):** 지금 4개(신혼·노인·한부모·대출 부부)에 4개를 더한다. 더할 후보는 은퇴 직전 부부, 다자녀 가족, 자영업 가구(지식베이스 밖 사례), 고령 1인과 자녀.
- **실행:** `python -m llm.eval`. 한 번에 한 가족씩, 비용 상한을 건다.

| 지표 | 뜻 | 측정 |
|---|---|---|
| 부적격 추천 수 | 자격이 안 되는 제도·상품을 추천 | 코드(판정 결과 vs 추천) |
| 근거 없는 제도 언급 | 카드에 없는 제도를 LLM이 말함 | G11 검사 실패 수 |
| 확인 필요 비율 | 너무 높으면 쓸모없음, 0이면 의심 | 판정 집계 |
| 방법 간 결과 차이 | 의미 있는 선택지인지 | 지금 결과 차이 검사(3개월) |
| 가족당 비용·호출 수 | | 사용 장부 |
